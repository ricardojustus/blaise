# Meet Events Contract — extension ⇄ Blaise listener

Binding contract between the Chrome extension (`extension/`, chunk C12) and
the app-side listener (C10/C11). The committed golden fixtures
(`extension/test/fixtures/wire_batch_golden.json` and
`expected_ingestion.json`) are the executable form of this contract: the
listener's acceptance MUST consume both. C14 adds the schema-v2 lifecycle
pair (`wire_batch_lifecycle_golden.json` + `expected_lifecycle.json`), with
the same dual-consumption rule. Spec: `specs/c12_meet_extension.md` (v4.2);
lifecycle/tracker semantics: `specs/c14_recording_automation.md`; design
decision: an internal decision record (as amended).

## Transport

- **Endpoint:** `POST http://127.0.0.1:18429/v1/meet-events`
- **Request body:** `{"iv": "<base64>", "ciphertext": "<base64>"}` — nothing
  else; there is no handshake, no ping endpoint, no plaintext anywhere.
- The listener binds loopback only. CORS handling is unnecessary (the
  extension's service worker fetch bypasses CORS via `host_permissions`).

## Crypto parameters (pinned)

| Parameter | Value |
|---|---|
| Cipher | AES-256-GCM (WebCrypto / CryptoKit) |
| AES key | `SHA-256(utf8(secret))` |
| IV | 12 random bytes, FRESH per message (retries re-encrypt; an IV never repeats) |
| AAD | `"blaise-meet-events-v1"` (utf8) |
| Ciphertext | GCM output with the 16-byte tag appended (WebCrypto default) |
| Ack key | `SHA-256(utf8(secret) ‖ utf8("ack"))` — domain-separated from the AES key |
| Ack MAC | HMAC-SHA256 |

The shared `secret` is generated by the app (32 random bytes, hex; stored in
the Keychain via the C2 SecretStore), shown in Settings with reveal +
regenerate, and pasted once into the extension's options page. Rotation =
regenerate in Settings, paste again.

## Signed acknowledgments (status codes are never trusted bare)

Every listener response to `/v1/meet-events` MUST carry:

```
X-Blaise-Ack: base64( HMAC-SHA256( ackKey, "ack-v1:" + base64(IV) + ":" + status ) )
```

where `base64(IV)` is the exact `iv` string from the request body and
`status` is the decimal HTTP status of THIS response (e.g. `"200"`). Base64
cannot contain `:`, so the delimiter is unambiguous. The signature is bound
to both the message (IV) and the status — a port-squatter can fabricate
status codes but not signatures.

Extension-side handling (pinned, tested):

| Response | Extension behavior |
|---|---|
| valid signed 200 | batch delivered; loss counters it carried reset; "connected" = age of this ack |
| valid signed 400 | batch dropped; its event count added to `poisonedCount` (rides the next batch) |
| valid signed 401 | keep buffering; after 3 consecutive → persistent "check secret" badge |
| valid signed 5xx | ring retry |
| ANY unsigned/invalid-signature response, any status | network-class → ring retry |
| network failure | ring retry |

Listener obligations: respond 200 only after the batch is durably accepted;
401 when decryption fails (wrong/stale secret); 400 only for a batch that
decrypts but is structurally unusable (it will never be retried).

## Batch plaintext schema (inside the encryption) — schema v2

```json
{
  "meetingCode": "abc-defg-hij",
  "capturedAtMs": 1781136000000,
  "droppedCount": 0,
  "poisonedCount": 0,
  "roster": [ { "displayName": "Maria Silva", "participantID": "pid-2", "isSelf": false },
              { "displayName": null, "participantID": "pid-1", "isSelf": true } ],
  "events": [ { "displayName": "Maria Silva", "participantID": "pid-2", "isSelf": false,
                "startEpochMillis": 1781135000000, "endEpochMillis": 1781135004500 } ],
  "schemaVersion": 2,
  "lifecycle": { "kind": "call-started", "atMs": 1781136000000 }
}
```

- `participantID` is optional everywhere (omitted when not scrape-able);
  values are opaque, per-device/session, and may change on rejoin.
- Events are CLOSED utterances only (coalesced: gaps ≤ 3000 ms merged,
  utterances < 500 ms dropped). Timestamps are wall-clock epoch millis.
- `droppedCount` / `poisonedCount` are cumulative undelivered-loss counters
  riding each batch; they reset after a batch delivers (valid signed 200).
  A volatile heartbeat (below) carries the current counters for honesty but
  never resets them.
- Dedupe id of an event:
  `meetingCode : participantID-or-displayName-or-"self" : startMs : endMs`.

### Lifecycle field (schema v2, C14 — OPTIONAL)

```json
"lifecycle": { "kind": "call-started" | "call-ended" | "heartbeat",
               "atMs": 1781136000000, "reason": "left" | "pagehide" }
```

- **Listener compatibility:** the ingestor accepts `schemaVersion ∈ {1, 2}`
  — a v1 batch is a v2 batch with no lifecycle (buffered pre-update batches
  still ingest). Everything else — AEAD parameters, signed acks, status
  semantics, ring, dedupe ids, correlation — is UNCHANGED.
- **`call-started`:** emitted on the lifecycle machine's idle→in-call
  transition; the batch carries the current roster plus the lifecycle field
  (`atMs` = transition epoch). Tab reloads re-fire it by design; the app
  debounces (it has the durable state). Ring-buffered like any batch.
- **`call-ended`:** emitted on in-call→idle, riding the existing
  final-flush batch (closed events + roster + lifecycle in ONE batch —
  atomic ordering, no extra POST). `reason: "left"` = the 1 s poll lost the
  in-call UI; `reason: "pagehide"` = the pagehide handler fired.
- **`heartbeat`:** emitted every 60 s while in-call, SKIPPED when any other
  batch shipped within the last 60 s (roster churn and speech already prove
  liveness). Heartbeat-only batches are **volatile**: one POST attempt,
  dropped on ANY failure — they never enter the ring (a stale heartbeat is
  worthless and would only displace real events; the 10k/200 caps stay
  honest). The listener never stores an unmatched heartbeat-only batch
  pending (content-free).
- **Replay/staleness:** lifecycle is a CONTROL signal, not content — never
  stored in `meeting_speaker_event`, never in the per-meeting seen-id set.
  The app-side tracker keeps ONE per-meetingCode monotonic guard over BOTH
  timestamp kinds (`atMs` and the per-batch `capturedAtMs`); a signal whose
  timestamp is ≤ the stored value advances nothing and fires nothing. The
  ±48 h batch freshness gate applies first.

### Tracker obligations (C14, app side)

For EVERY accepted code-carrying batch — correlated or not — the ingestor
forwards a per-batch liveness signal (meetingCode, `capturedAtMs`, plus the
lifecycle field when present) to the automation tracker, fire-and-forget
AFTER the ingest transaction (the signed 200 never waits on it). The
tracker owns the meet-start notification (with per-call suppression
memory), the end-debounced auto-stop, the signal-staleness watchdog, and
the resume grace window — semantics pinned in
`specs/c14_recording_automation.md`.

## Self model and the substitution rule

The wire NEVER carries a usable self display name:

- `isSelf: true` entries have `displayName: null` BY DESIGN. The localized
  self-tile label ("You"/"Você") is meaningless and never travels. The
  consumer MUST substitute `UserIdentity.name` — there is no name to fall
  back on.
- **Listener denylist (belt to the wire-level braces):** any incoming
  `displayName` in { `You`, `Você`, `you`, `você` } is treated as
  `isSelf: true` (covers a rotated self-tile label that escaped the
  extension's closed set).
- **Identity merge:** entries/events sharing a `participantID` are the same
  person. Merge them, preferring the NAMED form for display and the `isSelf`
  flag for substitution (a panel self row may arrive as an ordinary named
  participant when the tile link was missed — rule 3; merging by
  participantID resolves it).
- Known degradation (accepted): a partial self-detection miss (unlinked
  self tile + named panel row) splits the self vote across two identity
  keys; under C4's strict dominance the self cluster may stay unresolved —
  nil name, never a wrong name.

## Listener obligations (binding on C10/C11)

1. Decrypt per the pinned parameters; reply with signed acks per the table.
2. Apply the isSelf substitution and the participantID identity merge.
3. **Replay/dedupe:** AEAD does not prevent replaying a captured legitimate
   ciphertext. Keep a per-meeting seen-id set (retained with the meeting)
   keyed by the dedupe id above, and enforce a ±48 h freshness window on
   `capturedAtMs` (batches outside it are acked 200 but not ingested anew —
   or 400 if structurally stale by policy; never silently double-ingested).
4. **Golden fixtures:** acceptance must decrypt
   `wire_batch_golden.json` (both deliveries — the second is a byte-identical
   replay) with its `testSecret` and produce exactly
   `expected_ingestion.json`'s `activeSpeakerEvents` (ActiveSpeakerEvent
   Codable form, snake_case keys, `display_name` non-null after
   substitution), each event ingested ONCE. C14: acceptance must likewise
   consume `wire_batch_lifecycle_golden.json` + `expected_lifecycle.json`
   (v2 batch with lifecycle; replay ingests once, forwards a signal per
   accepted delivery, and the tracker's monotonic guard posts exactly ONE
   meet-start notification).

## Correlation rule (batch → meeting)

A batch matches the meeting with the same `meetingCode` whose
[startedAt − 10 min, endedAt-or-now + 10 min] window overlaps the events.
Ambiguity resolves to the greatest event-overlap duration. A meeting WITH AN
ACTIVE RECORDING SESSION correlates live (C11's case); otherwise correlation
happens at meeting close. Unmatched events are retained 7 days, then
discarded.

## Operational notes

- **Port collision:** if 127.0.0.1:18429 is taken by another process, the
  app logs the collision and does not serve; the extension's POSTs get
  unsigned responses → network-class → it buffers (ring, 10k events) and
  shows the buffering badge. No data is exposed: a squatter receives
  ciphertext only.
- **Buffering expiry (consequence of obligation 3):** `capturedAtMs` is
  stamped at capture and never refreshed, so a batch buffered through more
  than 48 h of app downtime is delivered and acked but then discarded by the
  listener's freshness window — buffering silently expires at 48 h.
- **Roster under-count:** tiles are captured continuously; the People panel
  only while open. The extension NEVER opens UI itself; without the panel,
  large calls under-count off-tile participants and off-tile speakers
  produce no events (documented; README suggests the one-click habit).
- **Residual risks (accepted, D13):** a squatter sees ciphertext only; a
  process that can read the browser profile's extension storage already
  owns the browser — out of threat model. Replay of legitimate ciphertext
  is neutralized by obligation 3, not by AEAD.
- **Consumer honesty:** until the C10/C11 listener lands, delivered events
  have no consumer and buffered events eventually ring-drop (sequencing
  fact of the file-first plan).
