# G12 — Recording UX (menu timer, level pulse) + Title Pipeline (v2)

**Goal (the user, 12/06/2026):** 1) menu bar item expands to a live timer while recording, colored/prettier record state; 2) in-app audio-LEVEL pulse indicator (replaces the static recording indicator) so "is it hearing me/others?" is answerable at a glance; 3) titles: a name set by the user must SURVIVE processing (today an ad-hoc meeting's start-time rename reverts to the date default — a capture-code bug, not a notes bug), and ad-hoc meetings with no user title get a short title PROMOTED from the notes engine's existing `NotesStructured.title`, used EVERYWHERE including the Evidence Store payload. G12 changes NO notes prompt: the title bug is fixed in capture code and the auto-title reuses a field the current prompt already produces.

## 0. Base & target tree (read first — non-negotiable precondition)

**This spec targets `main` (the merge target), NOT the current branch base.** The `g12-respec` worktree is checked out at the `main` merge-base, which is an ancestor of `main` and is STALE relative to it: in this worktree `BlaiseDatabase.swift` tops out at migration `v11`, there is no `v12`, `Domain.swift`'s `Meeting` has no `calendarEventId`, and the calendar layer is only partial (`CalendarSuggestions.swift` + `PreMeetingScheduler.swift` are present, but `CalendarDiagnostics.swift`, `UpcomingMeetings.swift`, and the G11 `calendar_event_id`/`scheduled_end_ms`/`grace_until_ms` columns from `main`'s `v12` migration are ABSENT). `main` has all of these (its highest migration is `v12`, registered in `BlaiseDatabase.swift`).

**Required before any implementation:** rebase `g12-respec` onto current `main` so the working tree actually contains `v12` (the calendar columns) and the full calendar layer. Every migration/column/file reference in this spec — `v13`, the `calendar` title tier, `calendar_event_id` — is written against post-rebase `main` and is only correct there. Do NOT register `title_source` against this stale base: the next sequential name here is `v12`, which would COLLIDE with `main`'s existing `v12` on merge and silently skip the calendar migration. After rebase, `v13` is the correct, additive next migration. If the rebase cannot happen first, this spec must not be implemented.

## 3. Title pipeline (item 3 — the precedence ladder, settled)

`meeting.title` is set by exactly one writer per tier, higher tiers never overwritten by lower:
1. **USER** — any explicit rename (G2's `renameMeeting`, whenever it happened: before, during, after processing). Mechanism: additive column `meeting.title_source TEXT NOT NULL DEFAULT 'default'` (`user|calendar|llm|default`); `renameMeeting` sets `user`.

   **THE BUG (capture-code, root-caused below — NOT a notes/finalize bug):** a rename made *during* recording reverts to the date default after processing. The v1 spec attributed this to "the processing pipeline writes the date-default at finalize"; that diagnosis is FALSE. `finalize` never writes `title` at all (`finalizeMeetingProcessing` writes only `status`/`lastProcessingError`). The actual revert is a **stale-snapshot full-row clobber in `performStop`**:
   - A meeting row is created at recording start carrying the date-default title (`RecordingController.startRecording`, the `Meeting(... title: title ?? Self.defaultTitle(for:) ...)` construction), and that *in-memory* `Meeting` value is captured into the actor's `ActiveSession(meeting:)`.
   - `renameMeeting` surgically rewrites the *DB row's* title (`fetchOne` → mutate → `update(db)`) but does NOT touch the actor's in-memory `session.meeting` (a value type — the live session still holds the start-time snapshot with the date default).
   - On stop, `performStop` does `var meeting = session.meeting` (the STALE snapshot, still date-default title), sets ONLY `endedAt`/`updatedAt`, and calls `MeetingRepository.update(meeting)`. That repository update is a full-row GRDB `meeting.update(db)` — it writes EVERY column from the stale struct, so the date-default title overwrites the renamed title already on the row.
   - `finalize` then runs and never restores it (it doesn't write title), so the revert is permanent.

   **THE FIX (capture-code):** `performStop` must stop writing a stale full row. Either (a) refresh from the DB first — `fetch` the current row, set only `endedAt`/`updatedAt`, then `update` — so concurrent column changes (the rename) are preserved; OR (b) replace the full-row write with a surgical `UPDATE meeting SET ended_at = ?, updated_at = ? WHERE id = ?`, mirroring the existing start-failure surgical write in the same file (`UPDATE meeting SET status = ?, last_processing_error = ? WHERE id = ?`). The implementer must audit every other full-row write of a possibly-stale `session.meeting` for the same hazard: the `resume` write-back currently does `MeetingRepository.update(meeting)` after a fresh DB `fetch` (so it is not stale today) but is still a full-row write and must be confirmed safe or made surgical; the `pause` path already uses the surgical `closePartAndSetStatus` transaction (no title column written — safe) and is the model to follow.
   - The `title_source` gate (below) governs the LLM/calendar **promotions**; it does NOT fix this revert. The core revert is the `performStop` clobber and is fixed in capture code regardless of `title_source`.
2. **CALENDAR** — the suggestion-matched title at start (sets `calendar`). This tier's writer is NEW and hangs off `main`'s calendar layer (per §0, post-rebase): the start path that already receives the suggestion title (`PreMeetingScheduler` passes `event.title` into start) writes `title_source = 'calendar'` alongside the title at row-create time on `main`'s schema (which carries `calendar_event_id` from the `v12` migration). It is NOT present in the stale worktree base and must not be wired against it.
3. **LLM** — ad-hoc meetings (`title_source == 'default'` after processing): the notes engine's EXISTING `NotesStructured.title` (already in the schema and the payload's `notes_structured`, produced by the CURRENT notes prompt) is PROMOTED to `meeting.title` + `title_source = 'llm'` when non-null/non-empty (trimmed, ≤ 80 chars — truncate with ellipsis). **No prompt change:** nothing copies `NotesStructured.title` to `meeting.title` today; G12 adds only that promotion. The notes prompt constant is NOT edited; G12 is OUT of any prompt-hash coordination.

   **Where the promotion runs (pinned, primary finalize path only):** the promotion belongs to the meeting's first `persistNotesAndFinalize` run (the only place a `default`-tier ad-hoc title is resolved from fresh notes) and MUST commit the new `meeting.title`/`title_source` to the DB row BEFORE the **stage-12 `persistNotes` markdown render** — not merely before the stage-13 payload build. Today stage 12 (`persistNotes`) renders the human-facing markdown via `NotesRenderer.render(... meetingTitle: meetingTitle ...)` and writes `notesURL`, where `meetingTitle` is `meeting.title` captured at run start (the date-default for an ad-hoc meeting); stage 13 (`finalize`) re-fetches `finalMeeting` and builds the payload from `finalMeeting.title`. If the promotion runs only before stage 13, the on-disk markdown keeps the date-default while the payload carries the promoted title — a divergence between the human notes surface (Floor 5) and the payload. The implementer promotes the title first, then renders stage-12 markdown from the promoted `meeting.title` (refresh the in-scope title after the DB write, or pass the promoted value into the render) so the markdown AND the payload both carry the promoted title from one source. The three deterministic re-mint paths (`renameMeeting`, `renameSpeaker`, `correctNameInNotes`) do NOT promote — they run on already-`ready` meetings whose `title_source` is settled and already render markdown and build the payload from the same `meeting.title` in one closure (internally consistent); they only propagate whatever title the row already holds.
4. **DEFAULT** — the date name.
- Regeneration: an `llm` title MAY be refreshed by a newer generation (still tier 3); `user`/`calendar` never.
- **Payload + markdown**: `meeting.title` flows to BOTH the human-facing markdown notes (rendered in stage 12) and the Evidence Store payload (built in stage 13 from the just-fetched `finalMeeting`) — an LLM title promoted on the primary run lands in BOTH surfaces in the SAME pipeline run. **Ordering (pinned):** the title promotion commits the new `meeting.title`/`title_source` BEFORE the **stage-12 `persistNotes` markdown render**, which is itself before the stage-13 `EvidencePayloadBuilder.build` and the `ImmutablePayloadWriter.write`/`finalizeMeetingProcessing` enqueue. "Before the markdown render" is the binding pin, not "before `build`" — there are four `EvidencePayloadBuilder.build` call sites (the primary finalize path and the three deterministic re-mints), and only the primary path renders markdown in a SEPARATE earlier stage than the build, so a "before build" pin alone would miss the stage-12 render and leave the on-disk markdown on the date-default title. A later rename re-mints (existing supersession).
- The G2 title-rename UI shows which source a title came from (subtle caption: "from calendar" / "suggested by notes" / nothing for user).

## 4. Acceptance criteria

- AC1 (bug): rename during recording → process → title SURVIVES (the field repro pinned end-to-end). The test must FAIL on the pre-fix code (drive the real `performStop` stop path with a renamed-mid-recording meeting and assert the DB title is the rename, not the date default — a stale-snapshot clobber must be observable as the failure mode); rename after processing survives regeneration.
- AC2 (ladder): each tier's writer pinned incl. the gate (default-writer / promotion refuses when `title_source != 'default'`; llm promotion only on default; calendar only at start; regeneration refreshes llm only). The `performStop` write is pinned to NOT carry the title column from a stale snapshot (refresh-from-DB or surgical), and the `resume` full-row write-back is pinned to preserve a concurrent title change.
- AC3 (llm title): promotion + truncation + non-null/non-empty gating + ordering across BOTH human-facing surfaces. For an ad-hoc fixture (`title_source == 'default'`, a non-empty `NotesStructured.title`) processed end-to-end through the primary `persistNotesAndFinalize` path: (a) the minted payload golden carries the promoted title (the promotion proven to happen before `EvidencePayloadBuilder.build`); AND (b) the persisted markdown notes file (`notesURL`) carries the promoted title (NOT the date-default), proving the promotion lands before the stage-12 `persistNotes` render — this second assertion FAILS if the promotion is pinned only before the stage-13 build. NO prompt-hash assertion here: the promotion reuses the existing `NotesStructured.title` and edits no prompt constant.
- AC4 (menu/meter, model layer): timer formatting + state mapping (tabular fixed-width); meter holder math (RMS smoothing, 10 Hz cap, silence-detection thresholds) pure-function pinned; leaf-observation isolation asserted (the Settings-fix observation test pattern — a tick/level publish must NOT invalidate the scene root).
- AC5: render/GUI checks batched to the deploy ask (menu expansion, meter pulse, silence tint — listed verbatim in the final report); Reduce Motion variants.
- AC6: suite green; migration additive (`title_source`, registered as `v13`). **`v13` is correct only against post-rebase `main`, whose highest existing migration is `v12` (the G11 calendar columns); see §0.** The acceptance test must confirm the new migration's registered name is the next sequential one AFTER `v12` (i.e. the tree being built against already contains `v12`), so registering against the stale `v11` base — which would name it `v12` and collide with `main` — fails the gate. Zero new engine calls (the title rides the existing generation). **Prompt hashes are untouched: the v1/v11/v2 notes-prompt hashes stay byte-identical and G12 ships in NO prompt-hash coordination — assert no prompt constant changed in the diff.**

## 5. Out of scope

Menu-bar waveforms; per-app audio source attribution; title editing from the menu; localization beyond EN/PT; any notes-prompt edit (D27 — the auto-title promotes the existing notes title, it does not ask the model for anything new).
