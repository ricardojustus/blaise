## Goal

A buildable, testable, committable skeleton: SwiftPM-based macOS app (no .xcodeproj), GRDB storage with the V1 schema, the per-meeting file layout, and the two canonical scripts (`build_app.sh`, `test.sh`) that every later chunk builds on. No pipeline logic, no UI beyond a launchable window.

## Domain model (BlaiseCore, all Codable + Sendable)

- `Meeting`: `id: MeetingID` (ULID string), `title: String`, `startedAt: Date` (non-optional — a meeting always has a start), `endedAt: Date?` (nil while recording), `source: MeetingSource` (`meet|zoom|teams|inPerson|imported`), `status: MeetingStatus` (`recording|processing|ready|failed|paused`), `attendees: [Attendee]`, `dominantLanguage: String?` (BCP-47), `asrProvenance: ASRProvenance?`, `lastProcessingError: String?`, `createdAt: Date`, `updatedAt: Date`.
  - **Status semantics:** `status` describes the *last full processing run*: `failed` = it did not complete (whatever artifacts DO exist — transcript without notes, say — remain valid and discoverable via the transcript/notes tables; nothing is implied destroyed). `ready` = transcript AND notes complete. Regeneration of a `ready` meeting must never regress it: a failed regeneration keeps `status == ready` and records the failure in `lastProcessingError`. C7 implements this contract; the column exists from v1. **Startup status sweep (C1-owned):** at DB open, stale `recording` or `processing` rows (no live run can exist at startup, single process) are set to `failed` with `lastProcessingError = "interrupted"`. The sweep NEVER promotes to `ready` — `ready` is minted exclusively by `finalizeMeetingProcessing` (one transaction with the handoff enqueue), which is what makes the ready⇒queued invariant airtight: a crash after notes-write but before finalize yields `failed`, and reprocessing (cheap, idempotent — artifacts already present are reused or regenerated) runs finalize properly. Partial-capture audio salvage on interrupted recordings is C11's concern (forward pointer). An in-flight *regeneration* is deliberately not representable in `status`: it is in-memory state, and a crash mid-regeneration leaves `ready` untouched — that is the no-regress rule operating. **`paused` (G9):** a durable held-open state on the `recording → paused → recording | processing` arcs. Manual pause finalizes the current capture part and writes `paused` in ONE transaction; resume opens a new part and writes `recording` in one transaction; End-from-pause flips `paused → processing` (its own transaction, before any dispatch) and runs the normal finalize→processing flow. The startup status sweep deliberately does NOT enumerate `paused` (it touches only `recording`/`processing`), so a `paused` row survives a crash/relaunch — the orphan-CAF sweep then encodes its parts for retention (floor 2) but WITHHOLDS the auto-kick for `paused`, and `dispatchProcessing` refuses `paused` outright: no path processes a paused meeting until End flips it.
- `Attendee`: `name: String`, `email: String?`, `source: AttendeeSource` (`meetExtension|calendar|manual`). JSON on the meeting row; produced by C12/C4, consumed by name resolution and the D4 payload's `attendees`. Independent of diarization — silent attendees exist.
- `ASRProvenance`: `engine: String`, `model: String`, `runtime: String`, `engineVersion: String`, `transcribedAt: Date`. Set whenever the transcript is (re)written (D5: engine identity = model + runtime).
- `TranscriptSegment`: `id: Int64?` (DB autoincrement), `meetingID`, `ord: Int`, `startSeconds/endSeconds: Double`, `speakerLabel: String` (diarization label; before diarization runs, the sentinel `TranscriptSegment.unattributed == "unattributed"` — single convention for C3/C4), `speakerName: String?` (resolved), `text: String`.
- `MeetingNotes`: `meetingID`, `markdown: String`, `language: String`, `generatedAt: Date`, `provenance: NotesProvenance`.
- `NotesProvenance`: `engine: String`, `model: String`, `pipelineVersion: String`. (The D4 payload composes ASR + Notes provenance.)
- `SearchHit`: `meetingID: MeetingID`, `segmentID: Int64`, `ord: Int`, `startSeconds: Double`, `snippet: String` (FTS5 `snippet()` with match delimiters pinned as `\u{FFF9}`/`\u{FFFA}` — unambiguous, never occurs in speech text; C10 maps them to styling). Consumed by C10 search UI.
- `HandoffItem`: `id: HandoffID` (ULID), `meetingID`, `payloadPath: String` (RELATIVE to the Blaise data root), `versionHash: String` (SHA-256 of canonical payload JSON — canonicalization is BLAISE'S OWN convention, implemented by C8's `CanonicalJSONWriter` and called via C7: sorted keys, integer-only numerics, minimal escaping, trailing `\n`. the knowledge graph re-hashes under its own convention at ingestion — the hashes are not shared keys. The payload MUST embed the meeting ULID as its `native_id`, so payloads for distinct meetings can never be byte-identical), `state: HandoffState` (`pending|delivering|delivered|failed`), `attempts: Int`, `createdAt: Date`, `lastAttemptAt/deliveredAt: Date?`, `lastError: String?`.
  - **State semantics:** `delivered` is the only state reached by SUCCESS. `failed` is retriable bookkeeping (C8 re-enters it) EXCEPT for two RESERVED `lastError` prefixes owned by C8 (registry constant `HandoffErrorClass`): `superseded:` is TERMINAL (a newer version of the same meeting was delivered — D12) and `damaged:` is wake-exempt quarantine (re-checked once per relaunch). Consumers (C10 retry-all included) MUST honor the prefixes; nothing is ever dropped SILENTLY — both states are visible. FIFO = `ORDER BY created_seq ASC`, where `created_seq INTEGER NOT NULL UNIQUE` is assigned monotonically inside the enqueue transaction (`MAX(created_seq)+1`) — a durable, VACUUM-stable, clock-independent enqueue order. The ULID `id` is the stable external identifier only; it carries no ordering contract.
  - **Crash recovery (C1-owned):** `delivering` is a transient claim by the single app process. `BlaiseDatabase` performs a startup sweep resetting any `delivering` row to `pending` (a `delivering` row at open time is by definition stale). Tested in AC2. (If a second process is ever launched directly, a sweep could reset a live claim and cause a duplicate push; accepted — the D4 receiver is content-addressed, so duplicate delivery is a no-op by contract.)
  - **Ready⇒queued invariant (C1-owned, C7-consumed):** marking a meeting `ready` and enqueueing its handoff happen in ONE database transaction, via `BlaiseDatabase.finalizeMeetingProcessing(meetingID:versionHash:payloadPath:notes:...)` provided by C1. Therefore no crash point can produce a `ready` meeting without a queued/delivered handoff row. A durable payload file without a row (crash before the transaction) is harmless: the meeting is still `processing`→swept to `failed` at startup, reprocessing regenerates identical bytes (immutable writer no-ops) and enqueues. Tested in AC2.
  - **Enqueue contract (C1-owned):** `enqueue` requires the payload file already on disk — the immutable writer writes via temp file + atomic rename (fsync'd) and `enqueue` verifies existence before inserting the row; at the stated durability bar (app-crash consistency; power loss may roll back commits but never corrupts) a `pending` row referencing a missing payload is not constructible by app crash. Should one ever exist anyway (power loss, manual file damage), it cannot wedge the queue: the payload is derived state, and C8's delivery loop re-materializes a missing payload file from the DB export path before delivering. On `UNIQUE(meeting_id, version_hash)` conflict, `enqueue` is a no-op returning the existing item (idempotent enqueue, consistent with D4). Both tested in AC2/AC4.
- `ULID`: minimal implementation (Crockford base32, 26 chars, time-ordered, monotonic within the same millisecond by incrementing the random component; on the astronomically-unlikely random-part overflow, spin to the next millisecond); no external dep.

## Storage (GRDB)

`BlaiseDatabase` wrapping `DatabasePool` at `<appSupport>/Blaise/blaise.sqlite` (path injectable; tests use temp dirs). **Durability bar, stated precisely:** WAL with `synchronous=NORMAL` (GRDB default). This is crash-consistent (app crash/kill -9 loses nothing committed) ; on full power loss the most recent commits may roll back but the DB never corrupts — acceptable because retained audio + deterministic reprocessing can regenerate any lost derived state, and the ready⇒queued invariant re-establishes queue rows on reprocess. Migrations via `DatabaseMigrator`, `v1`:

- `meeting`: columns per domain model (`attendees`/`asr_provenance` JSON TEXT). CHECK constraint on `source` (stable set). **No CHECK on `status`**: the status vocabulary is the one most likely to evolve (SQLite CHECK changes force a table rebuild); Swift enum decoding enforces validity at the boundary instead. Indexes: `started_at`, `status`.
- `transcript_segment`: FK→meeting ON DELETE CASCADE; UNIQUE `(meeting_id, ord)`.
- `meeting_notes`: PK `meeting_id`, FK→meeting CASCADE; `markdown`, `language`, `generated_at`, `provenance` JSON TEXT.
- `transcript_fts`: FTS5 external-content on `transcript_segment(text)`, tokenizer `unicode61 remove_diacritics 2`, synced via GRDB's `synchronize(withTable:)` (decision D8).
- `handoff_queue`: per HandoffItem; FK→meeting **ON DELETE RESTRICT** (belt-and-braces: V1 has no meeting deletion at all; if it ever arrives, undelivered rows must block it and delivered rows be handled explicitly); **UNIQUE(`meeting_id`, `version_hash`)** (idempotency is per-meeting: identical regenerations of the same meeting dedup; distinct meetings never collide — cross-meeting dedup would silently drop a handoff); CHECK on `state` (stable 4-value set, hard-floor-bearing — deliberate asymmetry with `meeting.status`, documented here); `created_seq INTEGER NOT NULL UNIQUE`; index `(state, created_seq)`; `delivered_endpoint TEXT` (nullable — the G5 destination identity a row's payload was actually written to, stamped in the same transaction as the `.delivered` transition and NULL on every other row; destination cleanup's deletion authority is keyed on it).
- `app_setting`: `key TEXT PK, value TEXT` (JSON values).

**Transcript authority:** `transcript_segment` (DB) is the single source of truth for the *corrected* transcript. `transcript.json` is an export artifact regenerated from the DB (C7), never read back. `raw_asr.json` is the immutable raw engine output.

Repository API: `MeetingRepository` (create/update/fetch/list by recency = `ORDER BY started_at DESC, id DESC` — **no delete in V1**), `TranscriptRepository` (replace-all-segments in one transaction with FTS sync, `deleteTranscript(meetingID:)`, `search(query) -> [SearchHit]`), `NotesRepository` (upsert/fetch), `HandoffRepository` (enqueue per contract above, nextPending FIFO, transition with attempt bookkeeping, startup sweep), `SettingsStore` (typed get/set). All async via GRDB's async API.

## Per-meeting file layout (constants + creation helper only in C1)

`<appSupport>/Blaise/meetings/<ulid>/`:
- `audio.m4a` — retained recording (primary system/mixed track). C11 may add a second synced track (e.g., `audio_mic.m4a`); `MeetingPaths` owns naming, and adding a file is additive — the retention contract below covers every `audio*.m4a`.
- `raw_asr.json` — immutable raw engine output (with ASRProvenance).
  - **C2 contract amendment** (`specs/c2_engine_interfaces.md`): `raw_asr.json` = raw output of the *current* ASR run, wrapped as `{provenance: ASRProvenance, payload: <engine-native JSON>}`; replaced atomically (temp+rename) on regeneration. "Immutable" — here and in "Transcript authority" above — means never edited in place; only replaced whole by a new run's output.
- `transcript.json` — DB export artifact.
- `notes.md` — human artifact export.
- `handoff/<version_hash>.json` — immutable, content-addressed payload snapshots; written temp+atomic-rename; writer fails if path exists with different bytes, no-ops on identical bytes; never overwritten; retained after delivery (V1).

**Retention guarantee (checkable):** no BlaiseCore API deletes or overwrites `audio*.m4a`; `MeetingPaths` provides no removal helper. Enforced by AC6.
