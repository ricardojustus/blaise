# G14 — `memory_digest` (machine-facing graph-extractor render)

**Goal.** Produce a second, machine-facing Markdown render of each meeting — the `memory_digest` — and ship it as a top-level field on the knowledge graph evidence payload, so the knowledge graph's knowledge-graph extractor mints clean typed entities and time-stamped facts from a purpose-built surface instead of from human notes or the raw transcript. The digest is the **PII firewall**: the knowledge graph's graph extracts from `memory_digest` ONLY — never the payload's `attendees[]`/`transcript` — so emails and the raw attendee list never reach the downstream graph.

**Contract ownership.** The digest's *internal* schema (the eight sections, the phrasing rules, the inline flags, the worked example) is **owned by the downstream knowledge-graph consumer** and specified in a separate maintainer brief (contract id `md-v1`) that lives outside this repo. This spec owns the Blaise side: the `md-v1` prompt that encodes the contract, the pipeline wiring, persistence, the payload field, the provenance stamp, and the Settings toggle. The envelope placement is settled in the handoff contract (top-level Markdown string, versioned at `provenance.memory_digest.prompt_version`).

**Floors.** 5 (notes are for humans; the digest is the distinct AI/the knowledge graph-memory surface — they are different renders, never conflated). 1 (no invented attribution — inherited). 3 + the product requirements (local-first; cloud only within the cost ceiling — the digest adds a second synthesis call, see the cost note + toggle). Plus the inherited G13 guarantee (no bare `S\d+` label reaches the digest).

**Status — this is a SPEC, not yet a build.** Every `app/` symbol named here (`generateDigest`, `systemDigestPromptV1`, `DigestPromptBuilder`, `DigestResult`, `DigestPromptVersion`, `DigestPendingClass`, the `digest-pending:` marker, `CloudSpendPurpose.digest`, the `memory_digest` column, `SLabelNeutralizer.neutralizeText`) is something G14 **builds** — none exists on the branch yet (the branch carries spec/state edits only). The build-side acceptance criteria (AC2, AC5, AC5c, AC6 — second call wired on both engines, digest G13-clean, persisted/re-materialized, H1 self-heal, receipted under the migrated `digest` purpose) and the Floor-8 / H1 mechanisms (digest-pending re-fire, byte-identical re-materialization of a stored `memory_digest`) are **obligations on the implementation**, verifiable only against the code once written — they are NOT claims that the code already exists. Every `:line` reference to an EXISTING file (SLabelNeutralizer.swift, NotesSynthesis.swift, ProcessingPipeline.swift, BlaiseDatabase.swift, CloudSpendReceipt.swift, Engines.swift, EvidencePayloadBuilder.swift, HandoffWorker.swift) was checked against this worktree and describes current state as the integration surface G14 extends; everything described as something G14 "adds"/"extends"/"fires"/"persists" is prescriptive. An implementation audit of G14 must run against the built code, not this document.

**Depends on G13.** The digest is model-generated Markdown, so it can contain S-labels; the inherited "G13-clean" guarantee is delivered by neutralizing every residual S-label in the digest string at the mint, **reusing G13's emphasis-aware label detector** (`SLabelNeutralizer.labelRanges`/`labelRegex`, SLabelNeutralizer.swift:127/131 — the same case-sensitive, `_S0_`/`**S0**`-aware grammar) behind a **new string-level neutralization entry point** G14 adds to `SLabelNeutralizer` (see §3 — the existing `neutralize(notes:labelMap:language:)` is struct-shaped and does not apply to a flat digest blob). **G14 implements only after G13 merges** (it reuses that detector + descriptor machinery).

## 1. Architecture (an internal decision record) — a SECOND synthesis call

The digest is generated by a **second LLM call in the same c6 summarization step**, fired *after* the notes call, taking the **degarbled transcript + the just-produced (name-substituted) `NotesStructured`** as input (the notes are the salience guide). The notes fed in are the name-substituted structured notes from `applyNameSubstitution`; G13 S-label neutralization happens *later* (inside persist), so the digest's own neutralizer pass — over the produced digest string — is what delivers the no-S-label guarantee, not the input notes (see §3 pipeline wiring). It is NOT a combined notes+digest prompt. Rationale:
- "Notes available as a salience guide" (brief §1) requires the notes as INPUT to the digest → a second call, not one combined output.
- A combined prompt would change the frozen `systemPromptV1/V11/V2` hashes (NotesSynthesisTests.swift:508/522/523) — a needless collision with G6 and G12. A second call with its **own** `md-v1` prompt keeps every notes pin byte-identical and lets the digest contract version independently.
- The two renders read the same meeting; producing the digest after the notes keeps them consistent and lets the digest contract (`md-v1`) bump without notes-version churn.

**Cost.** The digest is a second synthesis call ≈ the cost of the notes call (same engine; output is a compact structured digest). Honors the user's "synthesis quality beats cost savings on synthesis" — the digest feeds the knowledge graph memory and must use the same capable engine as the notes. Local-first still holds (on MLX it is a second local generation, no spend); on the cloud engine it is a second receipted call within the the product requirements ceiling, under the G7 announce-then-receipt discipline (a new `digest` spend purpose — see §3 for the CHECK-rebuild migration it requires). The cost is bounded by the toggle.

## 2. Settings toggle (the user, 13/06/2026) — Handoff → "Include memory digest", default ON

A permanent on/off toggle in **Settings → Handoff**, persisted in `app_setting`, default **ON**. It gates the whole feature for the publishing generalization:
- **ON (default):** the digest call fires; `memory_digest` + `provenance.memory_digest` ride the payload.
- **OFF:** no digest call (saves the second-call cost), and **no** `memory_digest` field on the payload. Per amendment §10, an absent `memory_digest` on a visible payload means "skip" to the knowledge graph — so turning it off cleanly degrades to no-digest, never a partial/garbled one.

The toggle is read at the digest-call decision point in the pipeline; flipping it affects forward renders only (it never rewrites already-minted payloads).

## 3. Mechanism

- **`md-v1` prompt (new, independent, frozen + pinned).** A new standalone constant `systemDigestPromptV1` in NotesSynthesis.swift, selected via a new `DigestPromptVersion` enum (`case mdV1 = "md-v1"`) + `DigestPromptBuilder.shippedVersion`. It encodes the knowledge graph contract: the **eight fixed-English `##` sections** (`HEADER`, `DECISIONS`, `COMMITMENTS`, `FACTS`, `STATUS`, `VIEWS`, `OPEN`, `POLICIES`) as *treatment groups* (sort a fact by how it behaves over time, not by topic; omit empty sections); the **global phrasing rules** (self-contained sentences with a full subject and no outside-pointing pronoun; ONE primary subject per line with secondary entities pushed to a trailing clause; name only durable entities — people/projects/companies/products/partners — never common nouns or quoted slang; canonical names on every mention; absolute dates only, resolved against `started_at_ms`; active voice with the actor named; DROP cited outside facts by default; split conditional/scoped/contrastive facts one-assertion-per-line; **content in the meeting's dominant language, never translated — only the `##` headers and the bracket flags stay English**); the **inline flags** `[confidential]` / `[suspected]` / `[external-claim]`; and the **must-NOT-contain** rules (no `attendees[]` dump, no emails, no `provenance`/metadata, no file paths, no device IDs; no bare diarization labels; no invented attribution). The prompt itself contains **no real data** — any illustrative fragment is fictional or omitted. It is hash-pinned exactly like the notes prompts; editing it bumps `md-v1` and that pin only.
- **Engine method (both engines).** Extend `SummarizationEngine` (Engines.swift:502) with a digest call — `generateDigest(_ request:purpose:) async throws -> DigestResult` (digest string + usage + the `md-v1` prompt version) — implemented on `ClaudeSummarizationEngine` (a second Messages call, ClaudeSummarizationEngine.swift) and `MLXSummarizationEngine` (a second `notes_driver.py`/digest-driver generation, MLXSummarizationEngine.swift). Input: the degarbled transcript + the produced `NotesStructured` + meeting metadata (`started_at_ms`, dominant language, meeting_type, vocabulary). The swappable-engine seam (the product requirements) is preserved — the digest rides the same engine the user selected for notes.
- **Digest S-label neutralization — a NEW public string-level entry point on `SLabelNeutralizer` (detector reused, surface net-new).** The digest is a single flat `##`-sectioned Markdown **string**, not a `NotesStructured`. `SLabelNeutralizer`'s only public surface today is `neutralize(notes:labelMap:language:) -> (NotesStructured, [Residual])` (SLabelNeutralizer.swift:47), which scans struct fields (title/summary/detailedNotes/decisions/actionItems[].owner/…) and bakes in two struct-shaped semantics that have **no meaning for a flat digest blob**: per-label stable-descriptor numbering assigned by scanning the struct's fields in order (`residualLabelOrder`, lines 173–195) and honest-empty OWNER clearing on action-item owners (`neutralizeOwner`, lines 72–85). The string-level pieces an implementer would need are **not callable from outside the module**: `replaceResiduals(in:labelMap:replacement:)` (line 156) is `private`; `residualRanges`/`labelRanges`/`labelRegex` (lines 112/131/127) are `internal`. So neutralizing the digest is **net-new public API**, not a call into the existing struct neutralizer. G14 adds a new public string-in/string-out function to `SLabelNeutralizer`, e.g. `public static func neutralizeText(_ text:String, labelMap:[String:String] = [:], language:String = "en") -> String`, that **reuses the existing emphasis-aware detector** (`labelRanges`/`labelRegex`) and the existing localized `Descriptors` (lines 199–221) to replace every residual `S\d+` in the blob with a content-free prose descriptor in the dominant language — the **prose** form for every occurrence (a digest has no action-item OWNER field, so the honest-empty owner semantics do NOT apply, and there is no struct field order to drive cross-field descriptor stability — descriptors are assigned by first-seen residual order within the single string). `containsLabel` (line 145) is the post-condition predicate the AC asserts. This is a deliberate, minimal addition to the G13 module (detector + descriptor reuse, new flat-string surface), justified because the digest is a string the notes-shaped neutralizer cannot consume — not gold-plating.
- **Bounded retry on transient failure (H1) — net-new, not inherited.** The notes call has **no** existing transient-retry to copy: `ClaudeSummarizationEngine` classifies a 429/529 as `.transient` in `mapHTTPError` (ClaudeSummarizationEngine.swift:284) and throws it; the only in-engine re-issue is the unrelated `max_tokens` output-budget retry (8_192→16_384, ClaudeSummarizationEngine.swift:142–166), which fires only on `stop_reason == "max_tokens"`, never on a rate/overload error; and at the pipeline layer a thrown `.transient` is not a fallback trigger (`EngineFallbackReason.isFallbackTrigger` returns false for `.transient`, Engines.swift:384), so a transient notes failure today propagates straight to the notes-pending self-heal — it is **not** retried in-place. The digest call therefore gets a **new, explicit bounded transient-retry built for it**: inside `generateDigest`, a 429/529 (or 5xx/`.transient`) is re-issued once after a short bounded backoff before the error is allowed to escape, modelled on the structure of the existing `max_tokens` bounded re-issue (one bounded retry, then give up) — NOT a claim of reusing an existing rate-limit retry. This is net-new work, not a copy. A transient blip therefore does NOT become a memory gap on the first wobble; only a failure that survives the bounded retry falls through to the digest-pending path below. (On MLX the new `generateDigest` applies the same one-shot bounded re-issue on a transient generation failure; a hard failure falls through identically.) Even if the bounded retry is skipped, the digest-pending self-heal path below is the actual H1 safety net — the bounded retry only shortens the window before that path engages.
- **Pipeline wiring.** In ProcessingPipeline.swift the digest call fires after the G2 name-substitution pass `applyNameSubstitution` (main path :1226; resume path `notesOnlyStages` :2225) and uses the **name-substituted `NotesStructured`** as the salience guide. Note the G13 `SLabelNeutralizer` does NOT run on the notes BEFORE this point: on the main path it runs *inside* `persistNotesAndFinalize` at stage-12 persistNotes (ProcessingPipeline.swift:1961), as the last write to `notes.structured`. So the notes handed to `generateDigest` are name-substituted but not yet G13-neutralized — that is fine, because the digest's no-S-label guarantee is delivered by neutralizing residual labels in the **digest string itself**, not by relying on neutralized notes as input. The digest's input notes may still carry an `S\d+` only as raw guidance text; the produced digest is what must be clean. Wiring: after `applyNameSubstitution` and before `persistNotesAndFinalize` (main path: between :1226 and :1230; resume path: between :2225 and :2229), if the toggle is ON, fire `generateDigest` (with its bounded retry) → take the digest string → run it through the **new `SLabelNeutralizer.neutralizeText` string entry point** (the same emphasis-aware G13 detector + descriptor machinery — see the neutralization bullet above — so a model-authored `_S0_`/`**S0**` in the digest is neutralized to the unattributed prose form) → hand the clean digest to persist+finalize. The same insertion is added to the notes-only resume path (`notesOnlyStages`, between :2225 and :2229).
- **Digest-pending sub-state on persistent failure (H1) — never a silent permanent gap.** A digest-call failure that survives the bounded retry is **non-fatal to the run**: notes + handoff proceed and the meeting is fully usable (Floor 8 — never block or lose a meeting). But it must NOT degrade into an indistinguishable, permanently-null memory render. The pipeline persists a **`digest-pending:` marker** — a new reserved `meeting.last_processing_error` sub-state registered in a `DigestPendingClass` enum alongside `NotesPendingClass` (NotesPendingClass.swift; same D17 no-string-scattering prefix registry). This sub-state:
  - is distinct from toggle-off and from legacy: a `digest-pending:` meeting *wanted* a digest and didn't get one this pass, whereas toggle-off/legacy meetings have a null `memory_digest` by intent;
  - **re-fires `generateDigest` on the next resume/regeneration — via a NEW digest-only resume path (net-new, not the notes-pending machinery).** The existing self-heal dispatch (ProcessingPipeline.swift:2043–2050) selects `WHERE last_processing_error LIKE 'notes-pending:%'` and routes every hit through `processNotesOnly`→`notesOnlyBody`→`notesOnlyStages`, which **unconditionally re-runs the notes engine call** (`generateNotesWithFallback`→`generateNotes`, :2167) — so it neither matches a `digest-pending:` marker nor does what a digest resume needs (notes-final, digest-only). G14 therefore adds a **separate digest-resume dispatch** keyed on the `DigestPendingClass.prefix` (`digest-pending:%`), fired from the **same self-heal triggers** that drive the notes-pending dispatch (app launch, API-key save, network-path restoration, an explicit regenerate — these triggers call the resume entry point, which now also runs the digest dispatch). For each `digest-pending` meeting it runs a **digest-only re-render**: load the stored degarbled transcript + stored `NotesStructured` (the `ready` meeting's final notes), call `generateDigest` (with its bounded retry), neutralize, persist, re-mint, and clear the marker on success. It does **NOT** call `generateNotes`. So re-materialization of a digest-pending meeting does **not** freeze `null` forever; the new digest-resume re-fires until a digest lands or the meeting is regenerated. Until then the payload simply omits `memory_digest` (absent ⇒ skip), which is the correct interim state.
  - The `digest-pending` resume is purely an *additional* digest attempt over the stored degarbled transcript + stored `NotesStructured` — identical inputs to the original attempt — so a success is consistent with the shipped notes, and the notes call is never re-run (a `ready` meeting's notes are final).
- **`digest` spend purpose — requires a CHECK-rebuild migration (G7 boundary).** The cloud digest call is receipted under a new `CloudSpendPurpose.digest` case. But the `cloud_spend_receipt.purpose` column is CHECK-constrained at the table boundary: migration v9 (BlaiseDatabase.swift:277) baked `CHECK(purpose IN (…))` into the CREATE TABLE SQL with the rawValues present **when v9 ran** (`generation`/`regeneration`/`validation`/`smoke`); SQLite does not update a column CHECK when a new enum case is added later, and `smoke` was specifically pre-provisioned in both the enum AND the v9 CHECK precisely so a gate "can thread it without a migration" (CloudSpendReceipt.swift:19–23). `digest` is NOT pre-provisioned, so on any migrated DB a `digest`-purpose INSERT would fail the frozen v9 CHECK. The additive column migration alone does NOT fix this. G14 therefore adds the new `digest` case to `CloudSpendPurpose` AND a migration that **rebuilds the CHECK** so `digest` is accepted — SQLite cannot `ALTER … DROP/ADD CONSTRAINT`, so this is a standard table rebuild (create `cloud_spend_receipt_new` with the widened CHECK derived from `CloudSpendPurpose.allCases`, copy rows, drop old, rename), or equivalently drops the column-level CHECK in favour of revalidating purpose at the write boundary. Either way it is an explicit migration step, not free.
- **Persistence (re-materialization determinism).** Store the clean digest string in a new additive nullable `memory_digest` column on `meeting_notes` (a new `BlaiseDatabase` migration, same C8 additive discipline as `meeting_type`), surfaced as `MeetingNotes.memoryDigest: String?`. Both schema changes — the additive `memory_digest` column AND the `cloud_spend_receipt` CHECK-rebuild above — register under G14's migration slot **`v14`** (one ordered slot may run both statements, or split as `v14`/`v14b`; what matters is that both land at G14's slot, not G12's): the live counter is `v12` (this worktree's migrator tail, BlaiseDatabase.swift:353), the in-flight G12 chunk lands `v13`, so G14's migration is `v14` — G14 must register at v14, not v13, to avoid colliding with G12 on merge. HandoffWorker re-materialization (HandoffWorker.swift:606, `rematerialize`) then reproduces the **stored** digest, never re-generates it — `EvidencePayloadBuilder.build` reads `notes.memoryDigest` and emits it presence-gated — so the `version_hash` is stable and a legacy/pre-G14 meeting (null column) re-materializes byte-identically with no `memory_digest` field (Floor 8).
- **Store-once / re-materialize-stored invariant (M5).** The persisted digest bytes are the single source of truth and change ONLY when (a) the pipeline genuinely re-runs the digest call — i.e. a `process`/`regenerate`/`digest-pending`-resume that actually invokes `generateDigest` — or (b) a deterministic name-edit rewrites the stored string in place (the edit-path rule in §4 below). They are **never** re-rolled by a spurious LLM call on a no-op re-render: a plain re-materialization (HandoffWorker) or a non-name edit (e.g. a title rename) reproduces the stored bytes unchanged. This is the mitigation that keeps supersession quiet — a no-op re-render must not churn `version_hash` and re-enqueue a "new" handoff that is byte-identical in spirit but freshly LLM-authored.
- **Payload + provenance.** In EvidencePayloadBuilder.payloadValue, add a **presence-gated** top-level `memory_digest` string (emitted only when the stored value is non-null) — `CanonicalJSONWriter` (CanonicalJSONWriter.swift:55) byte-sorts it into place automatically. Add a `provenance.memory_digest` sub-object alongside `provenance.notes`/`provenance.asr`, carrying at minimum `prompt_version: "md-v1"` (engine/model may mirror the notes call). When the column is null (toggle off, legacy, or digest-call failure), neither key is emitted.
- **Degenerate meeting.** A meeting with nothing memory-worthy yields a digest of `## HEADER` only (the envelope is always derivable). When the toggle is ON and notes were produced, the digest is always present (HEADER-minimum), never null/absent on the wire.

## 4. Edit path — name-changing edits rewrite the stored digest deterministically (M3)

A post-meeting edit must NOT leave the digest carrying a stale name while the notes show the corrected one. But re-running `generateDigest` on every edit would burn a second LLM call and break re-materialization determinism. The rule mirrors the existing deterministic re-mint paths (`renameSpeaker` ProcessingPipeline.swift:759, `correctNameInNotes` :871), which already re-render notes markdown + re-mint the payload with **no engine call**:

- **A name-changing edit** — a speaker rename (`renameSpeaker`) or a notes name correction (`correctNameInNotes`) — runs the **same deterministic `NameSubstitution` mapping over the STORED `memory_digest` string** (the digest is plain Markdown text; `NameSubstitution.applyToText`-style folded-word substitution applies to it exactly as it does to notes fields), persists the rewritten digest to the `memory_digest` column, and re-mints. **No new LLM call**; no md-v1 re-roll. The supersession is driven by the bumped `updated_at_ms` / new `version_hash`, exactly as the notes-side re-mint already supersedes. The corrected names therefore reach the knowledge graph's graph from the digest surface, deterministically, at zero added cost.
- **A non-name edit** — e.g. a title rename (`renameMeeting` :678) — does NOT touch the digest: it reproduces the stored digest bytes unchanged (the title is not part of the digest's entity surface). This keeps the M5 invariant: digest bytes move only on a genuine re-run or a name-edit rewrite, never on an unrelated edit.
- This preserves all three properties at once: re-materialization determinism (a stored string, deterministically transformed), corrected names (the substitution runs), and zero added cost (no second LLM call on edit).

## 5. Acceptance criteria

- **AC1 — `md-v1` prompt frozen + pinned; notes pins untouched.** `systemDigestPromptV1` is hash-pinned by a NEW independent test; the existing notes pins (v1 `49dc155e…` :508, v11 `de596e96…` :522, v2 :523, `v11.hasPrefix(v1)` :288) are byte-identical (G14 edits no notes constant). A structural test asserts the prompt enumerates all eight `##` sections and the must-NOT rules; the prompt contains no real identity.
- **AC1b — the load-bearing per-section rules are ENCODED in the prompt AND RESPECTED by a fixture digest (M2).** "Lists 8 sections" is not enough; the contract's per-section rules are what the knowledge graph's extractor depends on. Two complementary checks, each over FICTIONAL data:
  - **Prompt-encodes (structural, over `systemDigestPromptV1`):** the prompt text encodes (1) the **HEADER field set** AND the **`(none resolved)` token** the model must emit for the speaker field when no speaker resolved; (2) a **mandatory as-of date on every `STATUS` and every `OPEN` line** (a `STATUS`/`OPEN` line without an absolute date is contract-invalid); (3) **DECISIONS reversals stated as a dated, past-tense clause** (a reversal is a new dated line, not an edit of the prior line); (4) **one primary subject per line** (the global phrasing rule, named per-section so the extractor reads one entity per line).
  - **Fixture-respects (assertion, over a hand-authored fictional `md-v1` digest fixture):** a `## HEADER` whose speaker field is the literal `(none resolved)` token when the scripted meeting resolves no speaker; every `## STATUS` and `## OPEN` line carries an absolute date; a `## DECISIONS` reversal appears as a dated past-tense clause referencing the fictional prior decision; no line names two primary subjects. The fixture is the contract made concrete, so a future prompt edit that drops a rule fails the assertion, not just the hash pin.
- **AC2 — second call wired on BOTH engines, digest G13-clean, persisted, re-materializes.** End-to-end (with a fake/seam-injected engine, zero real cloud calls in the suite): the digest call fires after the notes on both the Claude and MLX engine seams, takes transcript + notes; the produced digest passes through the new `SLabelNeutralizer.neutralizeText` string entry point (§3) so the persisted/shipped digest carries no S-label — asserted via `SLabelNeutralizer.containsLabel` over the stored digest (the same emphasis-aware G13 detector, incl. `_S0_`); a digest input deliberately seeded with a residual `_S0_`/`**S0**` is shown clean on output; the digest is stored on `meeting_notes.memory_digest`; HandoffWorker re-materialization reproduces the stored digest byte-identically (and a null-column legacy meeting re-materializes with no `memory_digest` field).
- **AC3 — payload + provenance, presence-gated, canonical.** A digest-ON payload carries a top-level `memory_digest` string (byte-sorted) + `provenance.memory_digest.prompt_version = "md-v1"`; a digest-OFF / legacy / digest-failed payload carries NEITHER key and is otherwise byte-identical to today's. A degenerate meeting yields a `## HEADER`-only digest.
- **AC4 — Settings toggle, default ON, gates the feature.** The Handoff toggle persists in `app_setting`, defaults ON; OFF ⇒ no digest call and no payload field; flipping it affects only forward renders. Pinned end-to-end (ON ⇒ field present; OFF ⇒ field absent, no second call).
- **AC5 — PII firewall + floors.** A test asserts the digest surface contains no email-shaped token and no `attendees[]`-style list (the prompt forbids PII; the assertion is a backstop), and is G13-clean (no `S\d+` via the emphasis-aware detector).
- **AC5b — `[external-claim]` is DROP-by-default with a co-occurrence ban (M4).** `[external-claim]` is more than an inline flag — it carries an extraction contract. Two checks over FICTIONAL data:
  - **Prompt-encodes:** the prompt instructs the model to **DROP cited outside/third-party facts by default**, and — for any such line it *does* keep — to (a) mark it `[external-claim]` and instruct the extractor to **extract no entity/fact from that line**, and (b) keep third-party proper nouns **OFF any line that also names the user or the company** (no co-occurrence of a third-party entity with the user/company on one line).
  - **Co-occurrence ban (static fixture, genuinely testable):** a hand-authored fictional digest fixture containing a kept `[external-claim]` line; the assertion scans every `[external-claim]` line and fails if any of them also names the fictional user or company (third-party proper nouns must not co-occur with the user/company on one line). This is observable on a static fixture (the offending co-occurrence is *present* text), so it is a real check, not a vacuous absence.
  - **DROP-by-default (scripted-input path, not static-fixture absence):** a static fixture cannot prove a DROP — absence of a line is indistinguishable from "the author never wrote it," so an absent-line assertion over a hand-authored digest would be vacuous. Instead the DROP is exercised end-to-end through the digest seam with a **scripted engine**: a fictional INPUT (transcript + notes) carrying a clearly third-party cited claim is fed to a seam-injected digest engine **scripted to honor the md-v1 drop rule** (this exercises the wiring/contract path, with the honest caveat that it tests the scripted engine's adherence, not the real model); the assertion is that the produced digest does NOT surface the third-party claim as an attributed fact. The real-model guarantee lives in the prompt-encodes check above + the knowledge graph-owned contract; the suite (no real model) proves the *pipeline* carries a drop-honoring digest through to persistence unaltered. **Drop the earlier "a fixture in which a third-party claim is dropped" static assertion as unobservable.**
- **AC5c — H1: persistent digest failure is distinguishable AND self-heals via the new digest-only resume.** With a seam-injected engine forced to fail past the bounded retry: the run still completes (notes + handoff present, Floor 8), the payload omits `memory_digest`, and the meeting carries a `digest-pending:` marker distinct from a toggle-off/legacy null. A subsequent self-heal trigger drives the **new digest-resume dispatch** (keyed on `DigestPendingClass.prefix`, §3) which **re-fires `generateDigest` WITHOUT re-running `generateNotes`** — the test asserts the notes engine call count does not increase across the resume (the `ready` meeting's notes are final) while the digest engine call does fire; with the digest engine now succeeding, the digest is minted, stored, re-materialized, and the marker cleared — proving re-materialization of a digest-pending meeting is NOT a permanent null, and that the resume is digest-only (it does not route through the notes-pending machinery, which would re-run notes). (A transient-then-success case proves the new bounded retry alone recovers without ever entering digest-pending.)
- **AC5d — M3: a name-changing edit rewrites the stored digest deterministically; a non-name edit does not.** After a meeting is minted with a digest naming a fictional person, a `renameSpeaker`/`correctNameInNotes` edit that changes that name yields a re-minted payload whose `memory_digest` shows the **corrected** name (the stored string was deterministically rewritten, NOT re-generated — assert no second engine call fired and the digest is the stored bytes with the name substituted). A title rename (`renameMeeting`) re-mints with the `memory_digest` bytes **unchanged**. Together these pin the M5 invariant.
- **AC6 — cost receipted under a migration-provisioned `digest` purpose, suite green.** The cloud digest call is announced + receipted under a new `CloudSpendPurpose.digest` spend purpose (G7), within the the product requirements ceiling; the MLX path spends nothing. A test asserts a `digest`-purpose receipt **INSERTs successfully on a migrated DB** (proving the v14 CHECK-rebuild took — a `digest` INSERT against the un-rebuilt frozen v9 CHECK would fail, so this AC is non-vacuous). A `digest-pending` re-fire and a name-edit rewrite add **no** receipted spend beyond the one (re-)generation actually performed (the name-edit rewrite spends nothing). Full suite green.
