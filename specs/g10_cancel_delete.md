# G10 — Cancel Processing + Delete Meetings (v5.1)

**Goal (the user, 12/06/2026):** cancel processing mid-flight; delete meetings, with a confirm dialog.

**Floor 2 as refined by D23:** the SYSTEM never deletes autonomously. File deletion happens ONLY under a durable owner-intent record (the tombstone, §2) — row-absence proves nothing (a recreated blaise.sqlite makes every dir row-less; that scenario must preserve everything).

## 1. Cancel processing

- **Cancel commits FIRST, terminal writes preserve it:** the cancel action sets the token FIRST, then writes status `cancelled` in its own transaction, synchronously at click time (order pinned in AC1). Mechanism note: SubprocessRunner kill and the local stages ride Swift task cancellation; the in-flight cloud attempt is SHIELDED from task cancellation (the token binds at attempt boundaries only). The run's terminal-write paths — `recordFailure` (ProcessingPipeline.swift:1972-2011, the detached cancellation-surviving task) and `writeNotesPending` (1888-1903) — gain a status guard: they NEVER overwrite `cancelled` (read-check in the same write transaction). The existing `cancellationFailsWithCancelledTag` pin (PipelineTests.swift:528-552) is UPDATED to the new contract (spec-sanctioned change, not weakening: it now asserts `cancelled` preserved + no failed flip). The D17 self-heal gate keys on the preserved status correctly as a result.
- **End state = new durable status `cancelled`** (TEXT, no CHECK — the G9 `paused` precedent). The AUTO-KICK paths refuse `cancelled` (sweepOrphanCAFs kick, redispatchInterrupted, the startup interrupted-flip — a `cancelled` meeting is never flipped to failed/'interrupted' — notes-pending self-heal triggers, processKicker, listener seam); the USER's Process action and explicit regenerate are EXEMPT from the refusal (they are the sanctioned exits from `cancelled` — no deadlock). The detail view shows "Processing cancelled — Process" ; the user's Process flips cancelled→the normal dispatch entry.
- **Cancellation points, honest:** a checkpoint BEFORE each stage plus cooperative cancellation INSIDE the local heavy stages (whisper via SubprocessRunner's existing SIGTERM→SIGKILL path; diarizer's cooperative flag). **The current cloud ATTEMPT is never interrupted once sent, and cancel binds at the next attempt boundary** — no retry attempt, fallback hop, or new call starts after the token is set (the engine's max-tokens retry at ClaudeSummarizationEngine.swift:148-158 and the fallback chain check the token before each send); the in-flight attempt's existing bounded timeout (≤480 s worst case, stated honestly) is the ceiling on cancel latency — it is the last stage and short; a cancel during it takes effect when the call returns (usage recorded, receipt written, ceiling accurate — interrupting it would make Anthropic-side spend invisible to the ledger); the UI shows "finishing the current step…". Mid-stage local outputs are discarded; the write-only raw-ASR evidence envelope MAY have persisted (harmless, documented — it is evidence, not pipeline input).
- **No artifact resume (honest):** re-running a cancelled meeting re-runs the full pipeline (ASR included — minutes of local compute, no cloud cost until notes). Resume machinery is out of scope; cancel means "not now".
- **Races:** cancel and the run serialize through the single-flight chain's token: the run's stage checkpoints read the token transactionally; cancel-vs-completion = whichever commits first, the loser no-ops (a completed meeting stays completed). Cancel applies to ALL run classes via the same TOKEN, but the STATUS write is class-aware: first-run (process-class) cancel writes `cancelled` as specified; REGENERATION and notes-resume cancels keep those classes' status-untouched discipline — the run aborts at its next checkpoint and writes no STATUS (completed-stage artifact writes that already persisted — e.g. an updated transcript past persistTranscript — remain, consistent with crash-resume semantics; surfaced on the next successful run) (the meeting stays `ready` with its prior notes byte-intact; there is no `cancelled` state for a meeting that already has results, and the terminal-write guard simply never fires because regen-class runs have no failure-status write either — C1's no-regress rule). Cancel of an IDLE meeting (no run in flight) is a no-op, keyed on chain idleness, not status.

## 2. Delete meetings (tombstone-disciplined)

- **Refusal set:** delete refuses while the meeting is `recording` or an in-chain run for it is in flight (processing/regeneration/notes-resume — DELETE JOINS THE SINGLE-FLIGHT CHAIN, which serializes against all of these); "Cancel & Delete" sets the cancel token synchronously at click, with the status write CLASS-AWARE exactly as §1 (process-class → `cancelled`; regen/notes-resume → status-silent) (the in-flight run winds down at its next checkpoint/attempt boundary — never runs to completion first), then enqueues the delete, which the chain runs after the cancelled run exits. **`paused` meetings CAN be deleted directly** (their parts close unprocessed; G10 OWNS the cleanup: the delete operation calls the same per-meeting teardown the pause/End machinery uses (tracker manualControl, paused-class suppression record, controller linkage) — once G9 lands, that teardown entry is the integration point; until then the delete of a paused meeting is N/A (no paused state exists yet)).
- **Two-step confirm dialog (user directive):** names title + date; "This permanently deletes the recording, transcript, and notes from this Mac. Copies already delivered to your Evidence Store are not affected."
- **Order, crash-safe at every point:**
  1. In the chain slot, ONE DB transaction: DELETE all handoff_queue rows for the meeting (ALL states INCLUDING delivered — children first, satisfying ON DELETE RESTRICT; remote inbox files are untouched immutable history; local payload files live inside the meeting dir and go with it); DELETE segments (FTS cascade verified), parts, speaker events/renames, name-correction source links, notes, action-item state, the meeting row; INSERT `meeting_tombstone(id, audio_dir_path, deleted_at)`.
  2. Remove the audio directory.
  3. Delete the tombstone row (small follow-up transaction).
- **Crash windows:** kill before (1) commits → nothing happened. Kill between (1) and (2) → relaunch: the tombstone sweep removes EXACTLY the tombstoned dirs (owner intent, durable, path-specific) and then their tombstones. Kill between (2) and (3) → stale tombstone with no dir → swept harmlessly. DB loss/recreation → no tombstones → NO file is ever deleted (floor 2 holds by construction). The tombstone sweep LIVES in launch recovery beside the CAF sweep (CaptureRecovery) and is the only file-deletion site besides verified-encode's originals, step 2 itself, the existing bounded temp-file cleanups, the handoff worker's verified payload remove-and-rewrite (HandoffWorker.swift:587), and the sidecar replacement (MarkdownSidecar.swift:156-164) — the full inventory, stated precisely. POWER-LOSS (not kill) note: a torn filesystem can in principle resurrect directory entries after step 2 on non-journaled volumes — fail-safe direction (residue, never loss), documented.
- **In-flight delivery race:** the worker re-reads its queue row at claim/completion; a row deleted mid-delivery makes markDelivered a logged no-op (the remote file, if it landed, is immutable history — consistent with "delivered copies unaffected").
- **Residue accepted (documented):** `meet_seen_event_id` dedup entries (no FK, no content), receipts (meeting_id SET NULL by design). The detail view dismisses if its meeting is deleted; calendar suggestions may re-offer the time window (a suggestion is not the meeting).

## 2b. G9 integration (current state — G9 merged to main 12/06/2026)

G9 has landed (durable `paused` status, the holder mirror `pausedMeetingID` + the paused indicator window, the grace→Pause conversion via the H-3 `.paused` recording event). The two G9-dependent hooks this spec anticipated are now concrete and become acceptance-relevant for the G10 implementation:

- **The refusal set learns `paused` only where it must.** Delete's in-flight refusal (§2) keys on `recording` and an in-flight processing/regeneration/notes-resume run. A `paused` meeting has NO in-flight run (its parts are closed, no kick is owed — G9's sweep/dispatch refusal of `paused` is precisely why), so delete of a `paused` meeting is ALLOWED directly, not refused. The G9 cross-cutting refusal predicate (no path may PROCESS a `paused` meeting) is unchanged by G10: delete is not a processing path.
- **Delete of a paused meeting must clear the holder mirror.** Beyond the durable teardown (the shared per-meeting teardown entry §2 names: tracker `manualControl`, the paused-class suppression record, controller linkage), the delete must also clear `AppEnvironment`'s paused holder mirror — `pausedMeetingID` and the paused indicator window — or the refuse-everything predicate (G9 M-9: every start/resume refuses while a meeting is paused) outlives the deleted row and traps the user until relaunch. This is the same holder the G9 quit-keep-paused / relaunch-restore path owns; G10's delete clears it synchronously at the delete commit, mirroring how `resumeLostRace` teardown and the H-3 `.paused` event drive it.
- **Quit-dialog End intersection (G9 L-d):** the quit-keep-paused End kick is fire-and-forget and dies with the app, redispatching at next launch via interrupted-redispatch. A delete enqueued for a meeting whose End-kick is pending-at-next-launch is consistent: the tombstone (durable owner intent) wins — next launch deletes the dir and the redispatch finds no row to kick.

## 3. Acceptance criteria

- AC1 (cancel): the terminal-write guard pinned BOTH paths (recordFailure + writeNotesPending must preserve `cancelled`; the updated cancellationFailsWithCancelledTag); no post-cancel attempt/fallback send (token checked before each send — pinned with the recording engine stub); mid-ASR cancel → subprocess dead (kill-path pattern), status `cancelled`, NO auto-redispatch by any caller in the audited set (each pinned), Process re-runs the full pipeline; cancel during the cloud call → takes effect post-return with receipt + accumulator accurate; cancel-vs-completion both orders; cancel with no run in flight = no-op (idleness-keyed); a cancelled REGENERATION leaves the meeting `ready`, prior notes byte-identical (pinned); the click handler's token-before-status order pinned.
- AC2 (delete): full local erasure in one transaction incl. delivered queue rows + FTS (a mutant deleting the meeting row before queue rows must FAIL on RESTRICT); tombstone written in-transaction; paused-delete path; refusals (recording, in-flight chain) + Cancel & Delete composition.
- AC3 (crash windows): kill between txn and rm → relaunch sweeps ONLY the tombstoned dir; kill mid-txn → fully intact; a row-less dir WITHOUT a tombstone (simulated import-crash and fresh-DB scenarios) is NEVER touched — the C-1 pin.
- AC4 (UI/model): confirm dialog content; per-status control states; detail-view dismissal.
- AC5: suite green; pins byte-identical; zero engine calls.

## 4. Out of scope

Bulk delete; trash/undo (BACKLOG: restore-from-trash if field regret appears); per-part deletion; remote deletion; retention policies; artifact-resume for cancelled runs.
