# G5 — Generalized Handoff Destinations: Local Folder + Markdown Sidecar (v1)

**Goal.** Anyone's agentic system (Obsidian first) can consume Blaise output without SSH or the knowledge graph. Two additions; the SSH path is untouched. (publish_plan G5; D19.)

## 1. Design (settled)
- **Destination model:** `HandoffDestination` enum — `.ssh(HandoffSettings, markdownSidecar: Bool)` (existing SSH semantics incl. circuit breakers, plus the destination-independent sidecar flag) and `.localFolder(url: URL, markdownSidecar: Bool)`. Settings: a destination picker replacing the header's "the remote host" framing ("Evidence Store — where finished meetings are delivered"); SSH fields under the SSH choice; folder choice = NSOpenPanel with security-scoped bookmark persisted (sandbox-correct even though the app is not sandboxed today — bookmarks survive folder moves). The "Write Markdown sidecar (Obsidian-ready)" toggle is **destination-independent** (rendered next to the memory-digest toggle, OUTSIDE the per-destination fields) and applies to BOTH destinations; both read the single persisted key `handoff.localFolder.markdownSidecar` (name kept for migration), default ON.
- **Local delivery reuses the ENTIRE queue machinery** (states, retries, supersession, warning episodes (D21), Retry Now): the transport becomes a `LocalFolderTransport: HandoffTransporting` that (1) writes `<root>/<meeting-ulid>/.tmp-<hash>`, (2) verifies SHA-256 of the written bytes by **re-opening the temp from disk** (the local analogue of the remote `shasum`; an in-memory verify would be a tautology), (3) atomic-renames to `<hash>.json` via POSIX `rename(2)` (replaces an existing `<hash>.json` in one syscall — never remove-then-move, which would open a window where the visible file is absent) — the same verify-before-rename contract, same exactly-once guarantees, same inbox layout as an internal handoff note (the contract doc gains a "local destination" paragraph: identical layout, no host). **Atomicity is volume-dependent:** the temp and final share one directory, so the rename is a same-volume `rename(2)` — atomic w.r.t. concurrent readers on APFS/HFS+; on SMB/NFS it is protocol-dependent and iCloud-synced folders add a non-atomic sync layer (stated in the contract doc's local-volume caveat). Blaise never loses or duplicates regardless; the never-momentarily-absent property is best-effort on network/iCloud volumes.
- **Markdown sidecar (destination-independent toggle, default ON):** after the JSON delivery succeeds, deliver `<meeting-dir>/<slug(title)>.md` — YAML frontmatter (title, started_at ISO, attendees names, source: blaise, native_id, version_hash) + the already-rendered notes markdown.
  - **Local folder:** write the `.md` next to the JSON via `MarkdownSidecar.write` (one current sidecar per meeting; a slug collision between two distinct meetings sharing one folder gets a ULID suffix).
  - **SSH:** after the JSON delivery returns exit 0, UPLOAD the rendered `.md` to the SAME remote meeting dir via a second ssh invocation reusing the JSON's argv structure (user/host/identityFile) and transport, streaming the rendered bytes on stdin. Remote command (one argv element, login-shell re-parsed, every interpolated value single-quoted exactly like the JSON command): `mkdir -p '<remoteDir>' && rm -f '<remoteDir>'/*.md 2>/dev/null; cat > '<remoteDir>/<slug>.md'`. `remoteDir = remoteRoot + "/" + meetingID` (validated upstream: no `'`/`..`/`//`, ULID); `slug = MarkdownSidecar.slug(title)` is `[a-z0-9-]` by construction (the only new interpolated value, injection-safe; the worker asserts the charset and SKIPS rather than ever emit an unsafe command). The `rm -f '<dir>'/*.md` supersedes the prior-slug sidecar — the dir is per-meeting, so only this meeting's `.md` live there and the immutable `<hash>.json` history is untouched.
  - Sidecar delivery follows supersession (a newer version OVERWRITES the sidecar). Sidecar write/upload failure does NOT fail OR retry the delivery (JSON is the contract; sidecar is convenience) — it logs and retries on this meeting's next delivery.
- Errors: folder missing/unwritable/disk-full → the existing error classification (persistent after the D21 thresholds) → the warning surfaces. An unplugged external drive behaves like the remote host-offline: silent retry, eventual banner.
- **Superseded-payload removal at the destination (OPT-IN; `handoff.removeSupersededPayloads`, default OFF):** after EVERY successful delivery — deliberately not gated on a D12 supersession row, because in the correction flow the older payload was already DELIVERED, so no undelivered row exists to supersede and a supersession-gated cleanup would never fire — the transport removes the known superseded payload versions of THIS MEETING ONLY from the meeting's destination dir: the deletion candidates are the OTHER versions of this meeting that Blaise PROVED it delivered to the CURRENTLY ACTIVE destination — `handoff_queue` rows in state `delivered` whose `delivered_endpoint` (the delivery provenance, stamped in the same transaction as the `.delivered` transition) equals this destination's identity — excluding the just-delivered one and each re-validated 64-hex, so deletion authority never comes from a `.json` suffix nor from queue membership alone: a non-payload file, a hash-shaped name Blaise never wrote, another producer's JSON, a directory, a version that was only ever ENQUEUED (pending / failed / damaged / superseded — nothing was written anywhere), and a version delivered to a PREVIOUS destination (after a destination switch, a same-named file here belongs to somebody else) are all left alone. The destination identity is the destination INSTANCE — a monotonic epoch (`handoff.destinationEpoch`, absent ⇒ 0, bumped on EVERY destination change: kind switch, folder re-pick, SSH settings edit) plus the destination CONFIGURATION, never the route that answered: `e<epoch>:ssh:<user>@<host list>:<remoteRoot>` and `e<epoch>:local:<volume UUID>/<file id of the chosen folder>`. The configuration half is not the answering host because `handoff.hosts` is an ordered list of routes to ONE machine (C8) and a Tailscale→LAN failover must not read as a destination switch; the instance half exists because a DIFFERENT physical resource can be reachable under an identical configuration — a replacement volume mounted at the same path, a re-provisioned host at the same address — and must never inherit the previous one's deletion authority. The local folder is therefore keyed by its resolved resource identity rather than its pathname, which also keeps cleanup continuity across a folder MOVE (what the security-scoped bookmark is for); an unresolvable resource identity leaves the epoch carrying the distinction alone. A row delivered by a pre-provenance binary carries NULL, and a row stamped under a previous epoch or resource simply never matches — neither is authority. Every exclusion fails toward under-deletion, never toward deleting a file Blaise did not write here. (SSH: the command names those exact `<hash>.json` files, echoing each removal to stdout for the log, same argv/quoting discipline; local: enumerate, remove only names in that candidate set, never a directory, temp files untouched). With the toggle ON the destination holds exactly ONE current payload per meeting — a correction/regeneration REPLACES the delivered evidence instead of accumulating beside it (correction-flow audit finding #1). It is OFF by default (destination-independent toggle next to the sidecar toggle), so the shipped behaviour preserves the published immutable-history contract verbatim and an upgrade never begins deleting files at an existing install's destination. Default-OFF is operator-ratified (24/07/2026): the asymmetry decides it — an accumulating destination is trivially tidied later, deleted evidence is unrecoverable, and the primary consumer is an Evidence Store whose defining property is immutability, with downstream claims citing payloads by hash. Cleanup failure is failure-isolated exactly like the sidecar: never fails or retries the JSON delivery; logged; retried at this meeting's next delivery. The LOCAL `handoff/<hash>.json` snapshots under the meeting directory are NOT touched — immutability and re-materialization live there; the destination is a delivery target, not the archive. The contract doc's "older versions are not deleted" paragraph therefore STANDS as the default; consumers order by `updated_at_ms`, and removal is the opt-in.
- **Audio delivery (opt-in, default OFF; `handoff.deliverAudio`):** a destination-independent toggle ("Include audio recordings"), rendered with the sidecar/history toggles, delivering the meeting's retained audio files (`audio*.m4a` — system + mic + part-suffixed, exactly the C1 retention set) into the meeting's destination dir under their canonical names after the sidecar step. **Privacy is the headline, stated everywhere it matters:** default OFF; the Settings caption and README/privacy docs state plainly that enabling it copies recordings to the destination, and a destination that syncs (iCloud/network) means audio leaves the machine — the README's "no upload path for audio" promise is REWRITTEN to "no upload path for audio unless you explicitly enable audio delivery to a destination", never silently contradicted. Delivery semantics: failure-isolated from the JSON (audio failure/skip never fails or retries the delivery; logged; retried on this meeting's next delivery — and a toggle flipped ON later back-delivers on each meeting's NEXT delivery only, no retroactive sweep, stated in Settings copy); idempotent by size — retained audio is immutable post-encode, so a destination file whose byte length matches the local file is skipped (local: stat; SSH: one `wc -c` pre-check per file), otherwise local writes temp + `rename(2)` and SSH streams to a REMOTE temp, size-checks the received bytes against the locally known count, and only then renames, all in the same remote command (`cat > '<dir>/.tmp-audio-<name>' && [ $(wc -c < '<dir>/.tmp-audio-<name>') -eq <bytes> ] && mv '<dir>/.tmp-audio-<name>' '<dir>/<name>'` — a died stream whose `cat` still exits 0 leaves a short TEMP that fails the check, never a truncated file at the visible name; the temp carries the `.tmp-` prefix so the existing remote stale-temp sweep reclaims a crash orphan; names are the fixed canonical set — no new interpolated values, sidecar argv/quoting discipline). The payload JSON is untouched (no audio field — payload bytes and hashes are stable across the toggle); meeting deletion continues not to reach into destinations (audio included, stated in the contract doc).

## 2. Migration
Existing installs: current HandoffSettings map to `.ssh(...)` automatically; no behavior change; Settings shows SSH selected.

## 3. Acceptance criteria
- AC1: LocalFolderTransport unit tests — verify-before-rename (corrupt-on-write injected via the transport's read-back seam → no visible file, retry path), idempotent re-delivery, supersession closes older undelivered, `.tmp` hygiene.
- AC2: kill-mid-delivery (the C8 crash class) — kill between tmp-write and rename leaves only `.tmp-*`; relaunch redelivers; never a partial visible JSON. Reuse the C8 kill-test harness shape.
- AC3: sidecar — frontmatter golden (EN/PT titles incl. slug collisions: ULID-suffix on collision), overwrite-on-supersession, failure-isolated-from-delivery.
- AC4: D21 warning fires for a persistent local failure (folder deleted) with the folder-specific error class; Retry Now works.
- AC5: Settings round-trip — pick folder via bookmark, relaunch resolves it; SSH config untouched for existing installs (migration test on a settings fixture).
- AC6: end-to-end against a temp folder: meeting processed → JSON named by its hash (verify by recomputing) + sidecar present; payload bytes byte-identical to what the SSH path would emit (same builder — assert equality).
- AC7: suite green; pins unchanged; evidence contract doc bumped.
- AC8b (deletion authority): after a destination SWITCH, a same-named `<hash>.json` at the new destination survives (both transports — local: the file is byte-identical afterwards; SSH: no cleanup command is sent at all); the same holds when the destination is REPLACED under an unchanged configuration — a different folder at the same pathname (local: the foreign file survives byte-identical) and an SSH settings edit that re-identifies the machine (SSH: no cleanup command is sent) — because the delivered rows carry a previous instance's identity; a version that was only ever enqueued, never delivered, is never a candidate; the destructive toggle flipped OFF during candidate acquisition wins (the toggle is re-read after the candidate set is in hand, with no suspension before the delete call).
- AC8 (cleanup): deliver v1 → correct → deliver v2 leaves exactly `<v2hash>.json` + one sidecar at the destination (both transports; SSH via the recorded-argv harness); the default (removal OFF, key absent) preserves both files — asserted from the ABSENT key, since a seeded value tests the seed rather than the default; cleanup failure (undeletable file) delivers v2 successfully and logs; local `handoff/` snapshots untouched either way.
- AC9 (audio): toggle OFF = zero audio at destination (regression pin); ON delivers the full retained set incl. part files; size-match skip (no rewrite of an already-delivered file); audio failure never fails the JSON delivery; payload bytes hash-identical with the toggle ON vs OFF; README/contract-doc privacy wording updated (asserted by a docs grep test on the rewritten promise, keeping the claim and the behavior in one commit).
