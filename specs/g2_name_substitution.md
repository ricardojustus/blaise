# G2 — Name Corrections: Durable Store + Deterministic Substitution (v5.2)

**Goal.** Misheard names in NOTES get fixed deterministically and STAY fixed, with zero LLM judgment. Honest mechanism statement: ALL three motivating cases (Riso→Rosso, Caco→Caconi, SEMI→Sammy) are fixed by the **correction store** — the user corrects once, durably; the fuzzy owner-fix (rule 2) is a narrow bonus for longer names only (its thresholds reach none of the motivating cases — documented, not promised).

**Hard floors:** 1, 5. Substitution runs on notes fields and speaker labels — never transcript prose.

## 1. Context (verified)
- Speaker labels are non-interactive today (MeetingDetailView.swift:884); `renameMeeting` writes `meeting.title` directly, no rename table exists (ProcessingPipeline.swift:472-528). G2 builds speaker rename WITH a real durable table (§4).
- Diarization is persisted per meeting and reused on regenerate (the 2d78f71 fix) → `speaker_label` values are STABLE per meeting → rename rows can key on them.
- `speaker_name` can itself be a mishearing (SpeakerResolver.swift:204-209) — store/renames outrank it.
- riso (pt rank 1929), caco (766), semi (407) are everyday PT words; rosso↔riso d=2, caconi↔caco d=2, sammy↔semi d=3 (folded Damerau-Levenshtein).

## 2. The correction store
Additive migration: `name_correction` (id ULID, misheard_folded TEXT UNIQUE, replacement TEXT, everyday BOOL, source_meeting_id NULLABLE, created_at). No scope column. `everyday` is computed AT WRITE TIME by the G1 everyday test (lexicon/common-name membership of the folded key) and governs WHERE the row applies (§3 rule 1). Rows are created only via §5's explicit confirm.

**Write-time normalization (the chain/fixed-point discipline):** before insert, (a) the new replacement is resolved through existing rows once (if `replacement`'s fold equals an existing `misheard_folded`, store that row's replacement instead); (b) every existing row whose replacement fold-equals the NEW misheard key gets its replacement updated to the new replacement (transitive closure maintained flat); (c) inserting a key that fold-equals its own resolved replacement is refused (no-op rows can't exist); (d) WORD-LEVEL conflict refusal (NH-B): a new key that fold-equals any single WORD of an existing row's replacement — or whose replacement contains a word fold-equal to an existing key — is refused ONLY when the two rows' RESOLVED replacements differ (same-target chain refinements like riso→Rosso + rosso→Dana Rosso pass: (a)/(b) collapse them to one target; checks run BEFORE any (b) mutation, the (b) update applying only on accepted inserts) with explanatory copy naming the conflicting correction ('conflicts with "reyes → Sammy Reyes"'); the user resolves by deleting/adjusting the other row. The store is therefore cycle-free, one-hop, and word-compose-free; apply stays single-pass simple.

Settings: list + delete under the Glossary tab ("Notes name corrections"), showing each row's scope consequence ("applies everywhere" / "applies to owners and speaker labels only — '<key>' is an everyday word").

## 3. The substitution pass — pure, single-pass, idempotent
`NameSubstitution.apply(notes, speakers, attendees, store, glossary) -> (notes, report)` in generate, regenerate, and pending-resume. Fields: title, summary, detailed_notes, decisions[] (flat strings), action_items[].{owner,text}, ric_action_items[].{owner,text} (user_action_items post-G4). Segmentation: `enumerateSubstrings(.byWords)`; folds: C5 canonical; metric: folded Damerau-Levenshtein. **Hyphen guard:** a word-run whose enclosing characters abut `-` (intra-word hyphen context, "semi-aberto") never matches. **Quoted-span immunity:** balanced same-type pairs of double quotes (straight or curly) and «» and CURLY single quotes; STRAIGHT apostrophes are never quote delimiters (possessives/contractions/elisions — "Dana's", "Carlos'", "'90s" — make pairing undecidable; LLM-generated notes use curly or double quotes for quotation). Unbalanced = no immunity. Single pass over ORIGINAL spans; candidate matches collected first, overlaps resolved longest-run-first then leftmost; replacements applied together; replacement text is never re-scanned.

Rules (first-match-wins per span):
1. **Store hit.** Non-everyday keys: all fields. Everyday keys: OWNER fields and speaker labels ONLY (NC-1: "riso" prose stays laughter; "semi-aberto" protected by the hyphen guard regardless). **Context fixed point (NC-2, extended v5.2):** skip when the run already fold-equals the replacement, OR when the run is a sub-run of a neighborhood that fold-contains the full replacement (surrounding words up to the replacement's word count each side), OR when the run is a sub-run of a neighborhood that fold-equals ANY attendee/resolved-speaker full name (a store key never fires inside a person's already-correct full name — kills the rule-2→rule-1 surname-expansion composition) — `rosso→Dana Rosso` leaves "Dana Rosso" untouched on every application.
2. **Owner fuzzy fix** (owner fields only): candidates = resolved speakers + attendees. Fire iff: O fold-matches no attendee/speaker/canonical; exactly one candidate token T with d(O,T) ≤ (1 if len(T) ≤ 5 else 2), len ≥ 4; **common-name variant guard (NH-2): if O is itself a br_common_names member and d = 1, never fire** (Paulo/Paula, Adriano/Adriana class); replacement = candidate's full name; no-op when O already fold-equals it; ties no-op.
3. **Label polish** (labels + owner fields): fold-equal to a NON-limited, non-lexicon glossary canonical differing only in surface → canonical surface.

Report per generation (field, original, replacement, rule) into notes provenance JSON; shown in the info popover.

## 4. Speaker rename (built here, durable)
Additive migration table `speaker_rename` (meeting_id, speaker_label, anchor_ms INT, stale BOOL DEFAULT 0, name, created_at; PK meeting_id+speaker_label). `anchor_ms` = the MIDPOINT of the cluster's LONGEST segment at write time (an interior instant — robust to the boundary jitter that makes first-segment starts shift across diarization runs). UI: click a speaker label → rename popover → row upsert → labels re-render + payload re-mints (no engine call). Regenerate applies rename rows AFTER naming. Stability (NH-A, owned): with the persisted-diarization artifact present (all post-11/06 meetings), labels are stable and rows apply directly; on the MISSING-ARTIFACT fallback (fresh diarize — pre-11/06 meetings, ProcessingPipeline.swift:1149-1162), rows are RE-MAPPED by anchor (the cluster whose segments contain `anchor_ms`) and then — in the same transaction — RE-KEYED to the new label with `anchor_ms` recomputed from the new cluster, AND THE RE-KEY COMMITS BEFORE the fresh diarization artifact is persisted (a crash between them degrades to one more safe fallback run, never a direct-apply against old keys). OWNED RESIDUAL: under genuine re-CLUSTERING (an old under-clustered pair splitting), a single-containment anchor can map a rename onto the wrong split half — accepted at Medium under the honest claim; overlap-majority mapping is the eventual remedy (BACKLOG); no containing cluster, or two rows mapping to one cluster (both rows), → `stale=1`, NOT applied, label renders unnamed with 'rename needs re-confirmation'; a user re-confirmation clears `stale` and rewrites label+anchor. AC3 tests the artifact branch, the fallback re-map incl. re-key persistence across TWO consecutive regenerates, and both stale paths. Store rule-1/3 normalization applies to rename input too (one surface, no parentheticals).

## 5. Correct-name flow (mechanism explicit — NH-3)
Open "Correct name…" from a notes name (the occurrence picker defaults to the first occurrence with the count visible — SwiftUI's selectable Text exposes no tap-occurrence index; the engine is position-scoped and the picker chooses the occurrence) → popover (pre-filled with the unique rule-2 candidate when one exists). **Confirm applies POSITION-SCOPED (NH-C)**: the selected span is replaced directly; a toggle 'apply to all N identical occurrences in these notes' is shown with the count (default ON for non-everyday surfaces, OFF for everyday ones — prose risk stated inline). Persisted, re-rendered, re-minted. HONEST LIMIT, stated in the UI: an un-remembered correction fixes the CURRENT notes only — regeneration recomputes from the store, so 'Remember' is what makes it durable ('Regenerating will lose this fix unless Remembered' — and for an EVERYDAY surface corrected in PROSE, the copy states the stronger truth: 'remembered corrections for everyday words apply to owners and speaker labels; this prose fix is for these notes only'). **"Remember this correction" checkbox (default ON)** additionally writes the store row (§2 normalization; the everyday flag computed and its scope consequence shown inline before saving: "'semi' is an everyday word — this will apply to owners and speaker labels, not prose"). A separate "also add to glossary" link appears only when the surface would pass G1 admission (silent pre-check), never otherwise.

## 6. Acceptance criteria
- AC1 (pure function): per-rule pins incl. — everyday-key scoping (riso in prose untouched; riso as owner fixed), hyphen guard ("semi-aberto" intact with a semi store row), context fixed point (rosso→Dana Rosso: "Dana Rosso" stable, bare "rosso" expands once), write-time normalization (chain rows collapse; cycle refused), rule-2 honest misses (riso/caco documented NO-fire; a len-6 d-2 case fires), common-name variant guard (Paulo/Paula no-op), already-entity no-op, ambiguity no-op, quoted spans, overlap resolution, markdown intact.
- AC2 (integration): owner "SEMI" + store row → "Sammy" end-to-end, report present, re-mint, zero engine calls (recording stub).
- AC3 (UI/model): rename row round-trip + regenerate persistence (diarization reuse asserted); confirm-without-remember fixes the meeting only; remember writes the normalized row; glossary link gating both ways.
- AC4: pass runs in generate/regenerate/pending-resume (per-path integration).
- AC5 (idempotence): apply∘apply = apply property test over generated cases INCLUDING multi-word replacements; chained and word-overlapping store inputs are UNREACHABLE by §2(a–d) write rules — the property test generates stores through the write path (not raw rows), and a separate unit pins each §2 refusal incl. (d) both directions.
- AC6: suite green; regression pins byte-identical, asserted by an explicit identity check on the pinned notes with an empty store (empirical, not "by construction").
- AC7: migrations additive (both tables); old DBs open.

## 7. Out of scope
Transcript-prose substitution; automatic store population; fuzzy beyond owner fields; cross-meeting retroactive application; product/org fuzzy matching.
