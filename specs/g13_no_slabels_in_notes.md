# G13 — No S-Labels in Notes (v4.2)

CHANGELOG: v4.2 (2026-07-21) — C4 v5.6 room mode adds the reserved mic-cluster label class `M<n>`; the detector grammar extends to `(?<![A-Za-z0-9])[SM]\d+(?![A-Za-z0-9])` (both letters literal, case-sensitive — `m0` in prose is not a label). Everything else — layers, chokepoint, call sites — unchanged; an unresolved `M0` neutralizes exactly like an unresolved `S0`.

**Goal (the user, 12/06/2026, verbatim core):** "it CANT say S0… it KNOWS the context… If it CANT tell who said, just make a note on what was said not use S0 and S1 in notes (its fine in transcripts)." Field exhibit: a Zoom meeting whose participants were never resolved (no extension names; calendar missed it) — the notes say "S0/S1 said…" while the people are unnamed. the knowledge graph would ingest `S0`/`S1` as ENTITIES — a contamination class, not a cosmetic. The field exhibit came through the LOCAL engine; an internal audit record verdict note 2 records that the cloud-only v1.1 validation never reproduced raw-label leakage — so the load-bearing fix is an **engine-agnostic deterministic floor at the notes mint**, not a prompt instruction (which only shapes one engine's behavior).

**Floors:** 5 (notes are for humans — and for downstream the knowledge graph memory); 1 (no fabricated attribution — the model/neutralizer may surface only what the transcript or a resolved mapping grounds, never an asserted identity or role it cannot support).

**Scope decision:** G13 is **deterministic-only**. It does NOT edit the notes prompt. A prompt edit was considered and rejected on the evidence already on record in an internal audit record: the nearest precedent (`c6-v1.1`, the only prior notes-prompt edit aimed at this class) FAILED the fabrication hard floor — its cloud validation fabricated an action-item owner in 3/3 generations (verdict.md lines 45–46) — AND that validation was cloud-only, so it never exercised the LOCAL engine through which the field-exhibit S0-owners actually leaked (verdict.md lines 77–81). A prompt edit therefore (a) only shapes one engine's behavior and (b) has a measured fabrication-floor failure on this exact attribution problem. The user asked for content-preservation rather than confident role-attribution, and the deterministic neutralizer satisfies the floor on every engine. Consequently G13 touches **no prompt constant** and is fully OUT of the v1/v11/v2 prompt-hash collision that G6 and G12 coordinate (see AC3). A richer attribution feature, if ever wanted, is a separate independently-gated chunk.

## 1. The contract (two deterministic outcomes)

Notes text — every field, including action-item owners — must never contain a raw diarization label. For each label occurrence, deterministically:

1. **Resolved → the name.** If the speaker mapping resolved a name for that label, or the user renamed that speaker (a `speaker_rename` row), the label is replaced by the name.
2. **Unresolved → neutral, never invented.** Otherwise the label is neutralized: in prose, to a content-free neutral descriptor in the dominant language ("a participant", and "another participant"/"a third participant" by label index where the text needs to keep two unknown speakers distinct), or the statement is rephrased without a sayer where the shape allows ("It was noted that…"); in an action-item **owner** field, the owner becomes empty (the existing honest-empty pattern — the item keeps its text), and the neutralizer RETURNS that owner residual as a pure-function output (pinned by `SLabelNeutralizerTests`). SURFACING the residual to the user — a "notes mention an unnamed speaker" nudge in meeting info / the provenance report — is a DEFERRED follow-on (filed to BACKLOG): all four call sites today consume only the neutralized notes and drop the returned residuals. The no-S-label floor does NOT depend on that surfacing. The neutralizer NEVER invents a name, role, employer, or affiliation — an unresolved speaker is described only as a participant, never characterized.

This is exactly the user's ask: a resolved label becomes the name; an unresolved one becomes a note about what was said, not an `S0`.

## 2. Mechanism (two deterministic layers at the notes-mint seam, upstream of the render)

Both layers operate on `notes.structured`, **in place**, as the last write to that value before the render that consumes it. This ordering is load-bearing: `notes.structured` is rendered to markdown (`NotesRenderer.render`, ProcessingPipeline.swift:721/821/901/1964) BEFORE `build()` runs, and that markdown is a SECOND notes surface shipped to the knowledge graph (`summary_markdown` = `notes.markdown`, EvidencePayloadBuilder.swift:167), strictly MORE exposed than `notes_structured`. The same `notes.markdown` also reaches the remote host via the G5 sidecar (HandoffWorker.writeSidecar:430) and the on-disk notes file (`*.write(to: notesURL)` at 725/825/905/1975). Neutralizing only the value handed to `build()` would leave those surfaces carrying the label. So the neutralized value is produced once, before the render; render output, `build()` input, the DB upsert, the notes file, and the sidecar all derive from that one value.

- **Layer 1 — name substitution (extends G2, NEW wiring, not a free consequence of the rename flow):** build a label→name map from the resolved speaker mapping ∪ active `speaker_rename` rows (label→name), and replace label tokens in `notes.structured` fields with the name. This wiring is genuinely new: `renameSpeaker` (ProcessingPipeline.swift:759) today applies rename rows to the TRANSCRIPT (segments) and re-renders markdown from the EXISTING `notes.structured` UNCHANGED (the structured-notes value is not touched — an `S0` in `detailed_notes`/`summary`/an owner survives a rename today). G13 adds a label-substitution pass over `notes.structured` inside both `renameSpeaker` and the pipeline's notes stage. New entry point: `NameSubstitution.applyLabelSubstitution(notes:labelMap:)`, a sibling to `apply`/`applyNoteCorrection` (NameSubstitution.swift:86/524) — a label→name map is EXACT and case-sensitive (`S0`→`Dana`), not fuzzy. There is NO new UI: the existing G2 speaker-rename control feeds this pass, so the user's "I name S0 in a note and it populates" works via the existing rename → re-apply → re-mint flow plus this added pass.

- **Layer 2 — residual neutralizer (the hard floor):** post-substitution, any RESIDUAL label (no resolved name) is mechanically neutralized to the unattributed form per §1 outcome 2 — fail-safe, never a runtime throw. This is engine-agnostic: it strips literal labels regardless of which engine wrote the notes, so it holds on Sonnet AND the local MLX fallback.

**Emphasis-aware detection.** The detector must treat markdown emphasis runs (`_`, `*`, `` ` ``) as token boundaries. The naïve `/\bS\d+\b/` already MATCHES `**S0**`, `` `S0` ``, `- **S0:**`, `S0/S1`, `(S0)`, `S1:` (the `*`, `` ` ``, `/`, `(`, `:` are non-word characters, so word boundaries exist around the label). Its ONE genuine blind spot is **`_S0_`**: `_` is a `\w` character, so `\bS\d+\b` does NOT match an underscore-wrapped label. This form does not come from the renderer — `NotesRenderer.renderActionItem` (NotesRenderer.swift:309) emits owners as `- **bold**`, never `_italic_` — so `_S0_` can only arise when the MODEL authors underscore italics inside a prose field (`detailed_notes`/`summary`) that flows verbatim into `summary_markdown`. The detector therefore matches over an emphasis-neutralized projection (strip/space the `_ * `` ` runs, then `\b[SM]\d+\b`) OR the equivalent `(?<![A-Za-z0-9])[SM]\d+(?![A-Za-z0-9])` (v4.2: `M` = room-mode mic clusters, C4 v5.6). A label of any digit count is still a label (`S1000` matches as the whole token); a lowercase `s0` in prose is NOT a label (case-sensitive). One known theoretical-only gap: two labels glued with NO separator (`S0S1`) detect only the trailing `S1`, leaving the leading `S0` un-neutralized — unreachable in practice (the renderer emits separated owners like `- **S0:**`, and a model writing prose produces "S0 and S1", never `S0S1`), so no production input constructs it; filed to BACKLOG.

**Single chokepoint + structural guard.** A ship-ready `notes.structured` is produced ONLY by one pure function, `SLabelNeutralizer.neutralize(notes:labelMap:)` (layer 1 then layer 2). The FOUR forward mint sites each call it as the last write to `notes.structured` immediately before their render:
- `renameMeeting` — the TITLE rename (ProcessingPipeline.swift:719): re-mints a FRESH payload with a new `version_hash` + handoff row directly from `notes.structured`, so a label in pre-G13 stored notes would otherwise ship to the knowledge graph on a title rename. Not exempt.
- `renameSpeaker` — the speaker rename (:819).
- the notes-correction re-mint (:899).
- pipeline finalize — which deliberately SPLITS across stage 12 `persistNotes` (neutralizes at :1961, renders from `notesResult.structured`, UPSERTS the `MeetingNotes` row at :1974 + writes the notes file at :1975) and stage 13 `finalize` (RE-FETCHES `finalNotes` from the DB and `build()`s it at :1990), with `PipelineCrashHooks.maybeKill(.preFinalize)` (:1996) and a DB round-trip between them. The neutralizer runs at stage 12, as the value persisted — so the chokepoint is the `notes.structured`-mint SEAM, not a single contiguous `build()`-wrapping helper (a contiguous helper cannot subsume finalize without collapsing its crash boundary). Because every render, `build()`, `notes.upsert`, notes-file write, and the sidecar read `notes.structured` (directly, or via the DB row stage-12 persists and stage-13 re-fetches), neutralizing that one value covers all four sites and a `.preFinalize` kill re-fetches a clean, already-neutralized row on resume.

The structural guard against a FUTURE FIFTH forward site is mechanical, not convention: a **grep-guard test** asserts that no forward-path call to `NotesRenderer.render(...)` / `EvidencePayloadBuilder.build(...)` consumes a `notes.structured` that did not come from `SLabelNeutralizer.neutralize`. A new forward flow that renders or builds from a raw `notes.structured` fails that test — so cleanliness does not rely on the new author voluntarily adding a per-site pin. This is reinforced by the per-site end-to-end pins (AC1) at all four seams.

**Invariant scope — notes-content surfaces only.** The no-S-label payload invariant covers exactly the notes-CONTENT surfaces: `notes_structured` (all fields incl. owners), `summary_markdown` (the rendered `notes.markdown`), and `summary_text`. It EXPLICITLY EXCLUDES (a) `transcript[].speaker.diarization_label`, where S-labels are correct and required, and (b) `provenance.notes.name_substitutions`, which legitimately records a truthful audit entry `original:"S0" → replacement:"Dana"` (EvidencePayloadBuilder.swift:132-143) — a payload-wide `\bS\d+\b` scan would false-positive on that record. The invariant asserts the notes-content surfaces, not raw payload bytes.

**Persistence consistency (Floor 8).** The neutralized value is the SAME one rendered, built, and upserted, so a later re-materialization (HandoffWorker:614/618) reads the neutralized DB notes and reproduces the stored `version_hash` — never a divergent-copy mismatch that would quarantine a fresh (post-G13) meeting.

**Forward vs re-materialization.** `EvidencePayloadBuilder.build` is UNCHANGED — non-throwing, no forward-vs-rematerialize flag. Forward mint (the four sites) neutralizes at the seam. **Re-materialization of LEGACY payloads is EXEMPT** — HandoffWorker rebuilds a previously-minted payload to verify a stored hash; it reproduces stored bytes verbatim (S-labels included) and never neutralizes, because neutralizing would change the hash and quarantine a deliverable meeting (Floor 8 / "never lose a meeting's handoff"). Old meetings keep their S-label notes and their already-minted S-label payloads; the user regenerates on demand. The seventh `build()` site (CrashRunner/main.swift:345) is a dev/test seeding harness, out of scope. Transcripts are exempt at every layer.

## 3. Acceptance criteria

- **AC1 — neutralizer pure-function + per-site pins.** `SLabelNeutralizer.neutralize` and its detector are pinned as pure functions. Detector pin list MUST match `S0`, `**S0**`, `` `S0` ``, `- **S0:**`, `S0/S1`, `(S0)`, `S1:`, `_S0_`, and `S1000` (any digit count); MUST NOT match a lowercase prose `s0` (case-sensitive) or an identifier-embedded `S0Helper`/`AS0`/`S0x`. Layer 1: a resolved label→name map replaces every occurrence (structured + the rendered markdown). Layer 2: a residual prose label → neutral descriptor; a residual OWNER label → honest-empty, with the owner residual RETURNED as a pure-function output (the call sites drop it today; user-facing surfacing is a deferred follow-on in BACKLOG, and the floor does not depend on it). The payload invariant is an INDEPENDENT, test-only assertion over the neutralized mint value (not a `build()` throw): a forward-minted payload carries no label in EITHER notes-content surface — `notes_structured` AND `summary_markdown` — checked with the SAME emphasis-aware detector (asserting only `notes_structured` would pass a payload whose `summary_markdown` still carried a label), AND the invariant is scoped to notes-content (it does NOT flag `provenance.notes.name_substitutions` or `transcript[].diarization_label`). Pinned as a pure-function assertion over an S-label-bearing `notes.structured` fixture (covering structured + markdown + persisted-row consistency) AND exercised END-TO-END at EACH of the four forward sites — title rename (719), speaker rename (819), notes-correction (899), finalize (stage-12 neutralize :1961 → stage-13 build :1990, across its stage-12/stage-13 split). A **grep-guard structural test** asserts no forward-path `render`/`build` consumes an un-neutralized `notes.structured`.
- **AC2 — substitution glue (NEW, not a free consequence).** Rename `S0`→`Dana` → `notes.structured` carries `Dana` everywhere `S0` appeared (end-to-end on an S-label fixture; zero engine calls), proving the added label-substitution pass runs inside `renameSpeaker` over `notes.structured`, not only over the transcript.
- **AC3 — suite green; prompt pins byte-identical; zero prompt-hash coordination.** The full suite is green and EVERY existing prompt pin is byte-unchanged — the v1 hash (`49dc155e…`, NotesSynthesisTests.swift:508), the v11 hash (`de596e96…`, :522), the v2 hash (:523), and `#expect(v11.hasPrefix(v1))` (:288) — because **G13 edits no prompt constant**. There is no new prompt version, no blind gate, and no cloud spend. G13 is fully outside the v1/v11/v2 pin coordination that G6 (its v11 name-substitution edit) and G12 (its v1-base title edit) carry between themselves; the merge order of G13 relative to G6/G12 is irrelevant to every prompt pin.

## 4. Out of scope

Zoom extension signals; retroactive regeneration of old meetings (the user regenerates on demand) — old meetings keep their S-label notes AND their already-minted S-label payloads, which re-materialize verbatim (the neutralizer is forward-mint-only, never touches them); changing transcript labeling; **any notes-prompt edit** (the semantic "tier-2 role descriptor" approach is dropped per the scope decision above, grounded in an internal audit record — a future richer-attribution feature is a separate gated chunk).

## Fixtures

One synthetic, S-label-bearing structured-notes fixture in the established fictional universe (Vexatron Labs / Quoll Harbor, consistent with G8) — e.g. a partner-call note where one speaker resolves to a fictional name (`Dana Okonkwo`) and another stays unresolved. No transcript or model input is needed (there is no gate; all pins are deterministic). No real names, partners, meeting IDs, or content anywhere.
