## Goal

Two registered `SummarizationEngine` implementations (C2 protocol) and the prompt architecture that turns a speaker-attributed, corrected transcript (+ C7-computed `dominantLanguage`) into `NotesStructured` + `speakerNameMapping` — with the shipped DEFAULT chosen by a real bake-off on the sample transcript (the product requirements criterion 1), and B-2 cost-ceiling enforcement. Pipeline wiring is C7.

## Single language authority

`dominantLanguage` has exactly ONE producer: **C7's deterministic language-stats step** (C2's `NotesRequest.dominantLanguage` field). The computable rule, pinned here for C7: tokenize the transcript; count hits against two fixed small function-word sets (PT: que, não, uma, para, com, mas, isso, está… ~40 words; EN: the, and, that, with, this, have, what… ~40 words); majority wins; tie or both-zero → `pt` (the user's meetings default PT). Near-50/50 code-switched meetings get the majority language — B-1's per-meeting automatic choice, no user toggle. The LLM does NOT output a language field; the schema has none; the prompt RECEIVES the language as an instruction ("write every output field in <language>"). `NotesRenderer.render` receives the same value. One authority, no divergence, B-1 holds by construction.

## Runtime fallback contract (C2 amendment, recorded there by this chunk; D17 weight-class bound)

C2's "no silent engine swap" governs RESOLUTION (availability-time): the user's selected engine is never silently replaced before a run. This chunk amends C2 with the narrow RUNTIME exception for the summarization slot: when the resolved engine's `generateNotes` throws a fallback-trigger error (the pinned reasons below), C7 attempts the other registered summarization engine **exactly once (ONE hop, no cycling)** — **and only when that fallback declares `loadProfile == .lightweight` (D17)**. `SummarizationEngine` declares `var loadProfile: EngineLoadProfile { get }` (`.lightweight` / `.heavyweight(estimatedPeakBytes:)`): the Claude engine is lightweight (an HTTPS call); the MLX Gemma engine is heavyweight (declared 18 GB peak — the C6 KV probe measured 17.85 GB). **A heavyweight engine is NEVER auto-loaded**: when the only fallback is heavyweight, the notes stage resolves to the NOTES-PENDING outcome (owned by C7: transcript persisted and visible, no handoff enqueued, reserved `notes-pending:` marker on `lastProcessingError`, self-healing re-dispatch on app launch / API-key save / network-path restoration). A heavyweight engine still runs when it is the user's DELIBERATE primary selection — subject to its own memory gate (below). Rationale (D17, amending D15's posture): the auto-fallback cold-loading the 15.6 GB local model locked up the 32 GB machine twice in one day during back-to-back meetings; pending-then-self-heal preserves the transcript and the machine.

If a lightweight fallback also fails, the meeting's processing fails honestly with BOTH reasons recorded — "notes never SILENTLY blocked" is the guarantee; "notes always produced" is not claimable and every non-produced outcome is visible and remediable in the app. A successful fallback is RECORDED: NotesProvenance names the engine that actually ran, and a new `Meeting.processingNote: String?` column (this chunk's migration v3; C1 spec amendment line recorded by this chunk — distinct from `lastProcessingError`, which keeps failures-only semantics PLUS the reserved `notes-pending:` class) carries "fallback: <reason>"; **lifecycle: cleared at the start of every processing/regeneration run, set only by that run** (no stale notes). The C2 amendment text mirrors this bound.

**Trigger reasons (pinned constants in `EngineFallbackReason`; C7 matches on them, never on free-form text):** `.permanent(inputTooLong)`, `.permanent(outOfMemory)`, `.notAvailable(monthlyCeiling)`, `.notAvailable(insufficientMemory)`, and `.configurationMissing` (impl-audit H-1).

## Engines

### 1. `MLXSummarizationEngine` (id `mlx-gemma4-26b`, `.local`)

Gemma 4 26B-A4B-it, 4-bit MLX (`mlx-community/gemma-4-26b-a4b-it-4bit`, 15.6 GB weights, ~18 GB measured peak — fits the 32 GB machine only on a QUIET machine, which is why D17 classes it heavyweight and memory-gates every load; Qwen3.6-35B-A3B at 20.4 GB is REJECTED outright for memory risk, recorded in an internal decision record). Runs via a Python helper in the SAME venv infrastructure as C3's whisper engine. The requirements file is renamed `python_requirements.txt` (shared ownership, C3's references updated by this chunk); it grows mlx-lm==0.31.3 + outlines (pinned at implementation; transitive closure hand-enumerated under `--no-deps --require-hashes`; the torch-absent assertion re-run). Sentinel hash changes → rebuild is automatic.

**Cross-engine venv locking (scoped precisely):** ENGINE DRIVER runs (whisper_driver/notes_driver subprocesses) take a SHARED `flock` on `<dataRoot>/python/.lock` for the subprocess lifetime; provisioning destroy/rebuild takes the EXCLUSIVE lock and its OWN child spawns (`uv venv`, `uv pip`, import check) take NO lock — they run under the exclusive lock's protection (a generic in-SubprocessRunner acquisition would self-deadlock: flock conflicts across fds within one process). One acquisition per logical operation, one fd, children inherit nothing. Exclusive acquisition is try-then-wait≤30 s → `.transient("python environment busy")` (a rebuild never silently stalls minutes behind a transcription; C10's eager prepare retries later; single-user starvation risk accepted). C3's lock usage is upgraded to this scheme by this chunk and its spec text updated accordingly.

- Helper `notes_driver.py` (same contract style as whisper_driver.py): stdin = JSON request {transcript, meeting metadata, vocabulary, user identity, language, schema}; stdout = ONE JSON document conforming to the response schema, **enforced by Outlines constrained decoding** (`from_mlxlm`); exit codes 0/2/3/4, stderr detail. The schema travels in the stdin request as its RAW authored JSON (spliced, same device as the Claude request body): Outlines follows schema property order exactly like the cloud mechanism, a `.sortedKeys` round-trip alphabetizes it, and Python's `json.load` preserves wire-byte key order — wire order is pinned by a unit test on the driver payload. Same concurrent-drain, fixed 900 s timeout, cancellation-kills, orphan-marker patterns as C3 (shared `SubprocessRunner` — generalized, not duplicated).
- **Engine single-flight:** same actor + FIFO chain pattern as C3 (normative — two concurrent 15.6 GB loads on a 32 GB machine is the failure the chain prevents).
- **Input budget:** the helper computes EXACT token counts with the model's own tokenizer at request time (no chars heuristic — chars/3.5 UNDER-counts PT, the unsafe direction); no Swift-side pre-screen (a refusal gate needs an UNDER-count, and every cheap heuristic lands wrong-side for realistic PT inputs — the helper's exact tokenizer count, computed before any generation, is the only refusal authority and is cheap). Above `maxInputTokens` (KV-probe-calibrated, see smoke gate) the engine throws `.permanent(reason: EngineFallbackReason.inputTooLong)` (reason CONSTANTS — `inputTooLong`, `outOfMemory`, `monthlyCeiling` — pinned in code; C7 matches on them, never on strings) → the runtime fallback contract. Additionally, helper exit-4 with an OOM signature in stderr maps to `.permanent(reason: .outOfMemory)` (a fallback trigger — NOT `.transient`).
- **Memory gate (D17):** the engine declares `loadProfile = .heavyweight(estimatedPeakBytes: 18 GB)` (KV probe: 17.85 GB peak at the 24k budget). Before ANY weight load — at the top of `generateNotes`, before the driver subprocess spawns — it checks actual reclaimable headroom (free + inactive pages via `host_statistics64(HOST_VM_INFO64)`; `purgeable_count` is deliberately EXCLUDED — purgeable-volatile pages sit on the regular paging queues, so adding them would double-count pages already in `inactive_count`, inflating headroom in the unsafe direction; the dirty share of `inactive_count` remains a known optimism, absorbed by the margin; probe injectable as `availableMemoryProbe: @Sendable () -> Int64` for tests) against declared peak + a 2 GB margin; insufficient → `.notAvailable(reason: EngineFallbackReason.insufficientMemory)` WITHOUT loading anything. This protects even deliberate user-selected runs. `prepare()` is deliberately NOT gated: it provisions the venv and fetches the model to disk — no weights load there, and the launch-time eager prepare must keep working on a busy machine.
- Model cache: HF snapshot under the same `hfHomePath`; same integrity/suspect/wipe-repair predicates (shared code).
- prepare(): venv step (shared) + model fetch (15.6 GB; disk precheck 20 GB). Availability mirrors C3 semantics.
- EngineUsage: token counts from the helper; estimatedCostUSD nil (local).
- **Run-failure contingency:** the bake-off begins with a SMOKE GATE — (a) model loads + 1k-token constrained generation; (b) a KV probe: synthetic ~24k-token prompt prefilled + 100 tokens generated, peak memory recorded — calibrating `maxInputTokens` empirically (OOM → halve and re-probe; final value + evidence recorded). Smoke-gate failure (D5: runtime ≈ model) → local ships registered-but-unavailable with reason, cloud becomes default, the internal open-questions log records the gap; "at least one WORKING summarization engine" is a final acceptance requirement.
- Helper disables Gemma thinking/reasoning mode explicitly (deterministic notes; no hidden tokens billed against time).

### 2. `ClaudeSummarizationEngine` (id `claude-sonnet`, `.cloud`)

Anthropic Messages API via raw URLSession (no SDK dependency): `POST /v1/messages`, model `claude-sonnet-4-6` (constant; engine identity = model + runtime per D5), structured output via `output_config.format` json_schema (the current API mechanism, verified live; `output_format` is deprecated). **Schema property order is LOAD-BEARING:** structured-output generation follows schema property order, so the schema is spliced into the request body as its RAW authored JSON (title → summary → meeting_type → detailed_notes → decisions → action_items → user_action_items → speaker_name_mapping — analysis before conclusions, and the meeting-type classification committed BEFORE the notes are written: the same ordering mechanism pointed the right way, notes v2). A dictionary round-trip (`JSONSerialization`, `.sortedKeys`) alphabetizes the properties, forcing `action_items` to generate FIRST, which empirically collapses the entire document to a schema-valid EMPTY skeleton (live-probed 2026-06-10: 3/3 deterministic empties at 48 output tokens vs rich notes with authored order; prompt instructions and temperature changes do not recover it). Wire-byte property order is pinned by a request-construction test.

- Config descriptors: `apiKey` (`.secret`, required) — Keychain via C2 SecretStore; missing → `.configurationMissing`, engine `unavailable`.
- **Privacy boundary (per project policy): the request carries EXACTLY these fields and nothing else** — transcript text with speaker labels, meeting title, meeting date, attendee NAMES (no emails), the vocabulary list, the user's name and aliases (needed for user-item extraction), the dominant language. Asserted by a unit test over the assembled request. This is the Appendix-B-ceiling-bounded cloud exception, and it is the USER'S choice via Settings (the engine is registered, not default-forced; the bake-off picks the default honestly).
- Cost: $3/$15 per MTok (verified) → ~$0.074/meeting; 65 meetings ≈ **$4.78/month**, comfortably under the ceiling. `max_tokens = 8192`; **`stop_reason == "max_tokens"` → one retry at 16_384, then `.permanent("output exceeds retry budget")`**; input budget `maxInputTokens = 150_000` (same runtime fallback contract). Engine single-flight (actor + chain). Request timeout **300 s** first attempt, **480 s** for the 16,384-token retry attempt (16k tokens of output at realistic stream rates does not fit 120 s).
- EngineUsage from `usage.input_tokens/output_tokens` + computed estimatedCostUSD. Errors: 429/529/5xx (incl. `overloaded_error`) → `.transient`; 401/403 → `.configurationMissing(apiKey)`; 400 schema/content → `.permanent`; per-attempt timeout (300 s) → `.transient`. **Any response carrying `usage` updates the ledger — billed failures count.**
- **B-2 ceiling enforcement (C6 owns, machinery owned too):** schema migration `v3` (this chunk's, additive): table `cloud_spend {month_key TEXT PK, accumulated_usd REAL NOT NULL}`. `CloudSpendLedger(database: BlaiseDatabase)` — an actor whose `add(cost)` does the read-modify-write inside ONE `pool.write` transaction (atomic across concurrent calls; concurrency-tested). The engine receives the ledger by CONSTRUCTOR injection at the composition root (services are constructor-injected per C2; `EngineConfiguration` carries user config only). monthKey = "YYYY-MM" in America/Sao_Paulo. Ceiling setting key: `cloud.ceilingUSD` (default 20.0). At ≥ 100 % of `ceilingUSD` (default 20.0, settings-visible): the engine reports `unavailable("monthly cloud ceiling reached")` and generateNotes throws `.notAvailable(reason: .monthlyCeiling)` — a fallback trigger; with the shipped heavyweight-only fallback it resolves to the notes-pending outcome (D17), so notes are never SILENTLY blocked and complete automatically once the ceiling resets. At ≥ 80 %: a warning is logged and surfaced in Settings (C10). Month rollover resets. Ledger updates are written BEFORE returning the result (a crash can at worst under-count one call; accepted, noted).

## Response schema + prompt architecture (shared by both engines)

- **Response JSON schema** (Outlines and Claude json_schema both enforce; `additionalProperties: false` everywhere; NO min/max/length constraints — the Claude structured-output mechanism rejects them per the research, but `enum` on a string is supported; bounds are enforced post-parse in Swift where they matter): `{title: string|null, summary, meetingType: "one_on_one"|"budget_finance"|"project_review"|"decision_meeting"|"brainstorm_workshop"|"external_call"|"interview"|"general", detailedNotes, decisions: [string], actionItems: [{owner, text}], userActionItems: [{owner, text}], speakerNameMapping: [{label, name: string|null, confidence: "high"|"medium"|"low", evidence: string}]}`. NO language field (single-authority rule above). **`meeting_type` (notes v2, internal research notes):** a required strict 8-value enum authored BEFORE `detailed_notes` in the schema (classify-then-write: generation follows property order, so the model commits to a type before writing; `general` is the explicit "no strong cue" escape — an enum cannot leave the taxonomy). It maps to **`NotesStructured.meetingType: MeetingType?` — optional, presence-preserving Codable**: pre-v2 persisted notes decode `nil` and round-trip WITHOUT the key (treated as `general` where a value is needed), which keeps C8 payload re-materialization byte-exact for pre-v2 payloads; the payload builder emits `notes_structured.meeting_type` (additive, contract doc updated) only when the notes row has it. Engine maps into `NotesResult` + the C2-amendment field **`NotesResult.speakerNameMapping: [SpeakerNameProposal]`, `SpeakerNameProposal = {label: String, name: String?, confidence: ProposalConfidence, evidence: String}`** (Codable/Sendable/Equatable; additive; recorded in C2's spec by this chunk — C7 drops `low`-confidence proposals before apply()). **Decoding parameters pinned: MLX/Outlines = temperature 0.2 + top_p 0.9; Claude = temperature 0.2 ONLY (the API rejects requests carrying both temperature and top_p on Claude 4+ models — asymmetry deliberate, verified). No seed (APIs lack stable seeds; median-of-3 absorbs variance; the regression pin compares structured CONTENT with C7-defined tolerance, not bytes).** **Post-parse normalization: the engine enforces `userActionItems ⊆ actionItems` in code** (user items missing from the general list are unioned in; the dedicated section is a VIEW, and the renderer intentionally double-renders — stated, golden-tested).
- **Single-pass** (5–15k tokens fits; chunking would break dominant-language judgment and speaker mapping; research §3).
- **Prompt versions:** the system prompt is a FROZEN versioned snapshot (`NotesPromptVersion`: "c6-v1", "c6-v1.1", "c6-v2") — fixing a prompt is a new version, never an edit. Both engines resolve the version at generateNotes time from the GLOBAL `notes.promptVersion` setting (live read-through via `EngineConfiguration.globalValue`; unset/invalid → the shipped default) and record what ran in `NotesProvenance.promptVersion`. **Shipped default: c6-v1**, per two blind validations on the pinned sample: v1-vs-v2 (an internal audit record — the pre-committed gate required v2 to win or tie with zero new fabrications; the judge scored v1 ahead on faithfulness) and v1-vs-v1.1 (an internal audit record — judge given the FULL model input; v1.1 failed the fabrication hard floor and lost mapping plausibility). **c6-v1.1** = the frozen v1 text + ONLY the user's two field-fix blocks, appended (no v2 material; the decisions/action_items/user_action_items rules are untouched): CANONICAL NAME REPLACEMENT (a canonical vocabulary name REPLACES its mishearing outright everywhere a person appears — prose, summaries, decisions, action-item owners; phonetically-close + no competing referent → ONLY the canonical form, never parentheticals like "Marsa (Dana Marsh)"; competing referents keep the transcript form) and SPEAKER LABELS ARE NOT NAMES (S-labels never in prose/summaries/owners — resolved name, transcript-grounded name, or a neutral descriptor; labels live only in speaker_name_mapping). The v1.1 validation finding that survives the judge-protocol fix: the canonical-name instruction induces name OVER-ATTRIBUTION (invented owner, S2=Torres against the evidence, "Sammy Lee" picked from two vocabulary Sammys), not just spelling normalization — any future revision must subordinate canonicalization to the mapping-grounding rule and require uniqueness WITHIN the vocabulary list. **c6-v2** adds, on top of every v1 rule: a MEETING TYPE block (classify as exactly one of the 8 enum values BEFORE writing, title+attendees+content cues per type, `general` as the explicit escape, fixed tie-break order interview > budget_finance > external_call > one_on_one > decision_meeting > brainstorm_workshop > project_review > general); a NOTES STRUCTURE block (per-type section plans rendered as "##" headings inside detailed_notes, in the dominant language; THE PLAN IS A MAXIMUM, NOT A QUOTA — empty sections are omitted, the anti-hallucination rules apply inside every section); type-specific fabrication bans (budget tables carry ONLY spoken amounts; external-call "signals" must quote, never infer mood; interview notes NEVER evaluate or recommend); the canonical-names-in-notes rule (a transcript name phonetically adjacent to a vocabulary person with no competing referent takes the canonical spelling; competing referents keep the transcript form); and the no-raw-label rule (S0-style labels never in prose or as owners — resolved name, grounded name, or a neutral descriptor; labels live only in speaker_name_mapping).
- System prompt v1 (frozen; **`NotesProvenance` gains `promptVersion: String`, decode-default "" — additive C2-type amendment; pipelineVersion stays C7's**): role (faithful meeting scribe), the **language rule** (B-1: ALL output fields in the dominant transcript language; company and product terms/quoted phrases verbatim in original language), the **formatting rules** (Brazilian conventions: DD/MM/YYYY, month-name when ambiguous; 1.000,00 Brazilian numbers in PT notes, 1,000.00 in EN notes; R$/US$ as spoken, never converted; 24 h times), **anti-hallucination** (only content from the transcript; empty sections are empty — the renderer adds the localized "none" markers; never invent owners — an action item without a clear owner uses the speaker who committed to it or stays out of actionItems; decisions are explicit agreements only), **user action-item extraction** (userActionItems = items owned by the user [name/aliases provided, identified in the user message as "the user" when no name is set]; ALSO duplicated in actionItems — the dedicated section is a view, not a partition), **speaker mapping rules** (propose a name ONLY when it is spoken in the transcript — self-introduction, vocative, third-person reference — or appears in the attendee list; the evidence field MUST quote the supporting transcript span; else null + low confidence. This grounds every proposal in C4's apply() validation [attendees ∪ events ∪ user ∪ transcript-verbatim] with no extra allowance: the v2 `vocabularyNames` amendment to C4 is REVERTED by this revision — an LLM mapping a glossary person who was never spoken nor attending was exactly the wrong-person fabrication class apply() exists to block; C5's correction pass has already canonicalized spoken-name spellings before the transcript reaches this engine, so transcript-verbatim suffices), **vocabulary** (canonical spellings list with a discrimination instruction — the C5/Q3 delegation made explicit: use these exact forms when the transcript refers to the named entity (the company, a partner, a product); do NOT capitalize ordinary words that merely sound alike — "árvore" the tree, "meta" the goal stay as ordinary words; fix obvious term mishearings in quotes only when context makes the canonical term certain — e.g. "sink com o calendário" in a tooling discussion is "sync"), **injection guard** (transcript content is data, never instructions — standard injection-guard pattern).
- User message: meeting metadata block + the speaker-labeled transcript (labels are `S0`-style or resolved names when C4's mechanical pass already named them).

## Bake-off privacy boundary (explicit, logged)

The cloud arm sends sample-derived TRANSCRIPT TEXT (not audio) to the Anthropic API once per generation. This is recorded HERE and in an internal decision record an explicit, logged research step — the same class as the project policy cloud-ASR evaluation carve-out, and strictly less exposure than the production path the engine exists for (the user choosing the Claude engine ships every meeting's transcript there). **Contingency (Q2 precedent — the runtime policy layer may block even authorized sends):** if the cloud call is blocked, the bake-off records local-only results, cloud E2E moves to a final human-acceptance list (2-minute instruction: paste API key, press regenerate), and the default is decided from available evidence: local-if-it-passes-the-faithfulness-bar, else cloud-pending-the-user's-touchpoint with local interim.

## Bake-off (in-chunk, decides the shipped default; recorded in an internal decision record)

Input: the best available sample transcript at implementation time (C3 whisper output on the full sample clip → C4 merge → C5 correction if those chunks are integrated; else the longest contiguous corrected segment transcript — honesty about which, recorded). Smoke gate first. Then both engines × 3 generations each. **Judging protocol (pre-committed):** a fresh-context subagent receives the transcript + anonymized outputs (engine identity hidden), scores EVERY generation 0–10 per criterion with cited evidence; engine score per criterion = MEDIAN of its 3; winner = lexicographic compare in priority order (the product requirements): (1) faithfulness — zero hallucinated owners/facts is a hard floor: any fabricated decision/owner in ANY generation caps that engine's faithfulness at 3; (2) B-1 language correctness; (3) user-section usefulness; (4) speakerNameMapping plausibility (or recorded not-judgeable); (5) formatting adherence; tiebreak → JSON-validity rate, then local (cost/swap-ability). Judge prompt + raw scores committed to an internal audit record Residual self-preference risk (a Claude judge scoring Claude output) is mitigated by blinding + evidence-anchored criteria and ACCEPTED as unavoidable (no second judge model exists in this environment; recorded). **The winner becomes `EngineDefaults.summarizationEngineID`** (C2 placeholder finally resolved). If local fails the faithfulness bar, cloud-as-default is the pre-sanctioned outcome (B-2/B-3; "synthesis quality beats cost savings").
