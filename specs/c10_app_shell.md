## Goal

The real app surface, replacing the C1 placeholder window: a beautiful, browsable notes library (D16 design), meeting detail with rendered notes, full-text transcript search, Settings (engines, identity, handoff, cloud ceiling), the file-first import entry, immediate notes surfacing on processing completion, pipeline/queue status surfaces, and the meet-events listener (C12's contract consumer). Dark-first, one quiet accent, macOS 26 Liquid Glass — restrained.

## Structure (BlaiseApp target; BlaiseCore stays UI-free)

- **`LibraryView` (D16 Direction A):** NavigationSplitView — sidebar (Library: All Meetings, This Week, My Action Items; later: projects — V1 ships the three smart groups only), center list (day-grouped rows borrowing C: title, time+duration, attendee names line, B's borrow: action-count badge + processing-state glyph), detail = `MeetingDetailView`.
- **`MeetingDetailView` header (V1.1):** the meeting/calendar title rendered prominent and INLINE-RENAMEABLE (click → edit in place; Enter/focus-loss commits, Escape cancels — no button; calendar-sourced titles equally renameable, the rename wins); attendees as human NAMES — calendar sources often deliver the email AS the name, so `AttendeeDisplay` prettifies the local-part ("robin.cole" → "Robin Cole") and the full addresses live in a tooltip; an audio PLAYER (AVPlayer; play/pause + scrubber + elapsed/total + a compact 1× / 1.5× / 2× speed pill) over the retained `audio.m4a` at the top of the notes page. The retained file is 16 kHz mono AAC; AVPlayer resamples it to the output-device rate, so it plays at NATURAL pitch on any device (no chipmunking). The speed control is pitch-PRESERVING: the item's `audioTimePitchAlgorithm` is `.spectral` (Apple's voice-quality time-stretch) and playback drives `player.rate`, so 1.5×/2× sound natural rather than sped-up-in-pitch. The chosen speed is sticky across meetings (UserDefaults, the `DesignSelection` idiom; pure `PlaybackSpeed` model + resolution in BlaiseCore). Captured meetings also retain `audio_mic.m4a` (mic track, kept for ASR/regeneration) which V1 deliberately does NOT mix in (the system track carries the meeting; limitation documented in code).
  - **Rename semantics (the decided rule):** `title` is a payload-builder input AND the renderer's H1 fallback, so a title edit is a CONTENT mutation — `updatedAt` bumps (C1 v6.9; the meetingCode metadata carve-out does NOT extend to title). On a `ready` meeting, `ProcessingPipeline.renameMeeting` (single-flight chain — never interleaves with a run) re-mints DETERMINISTICALLY: no engine call (structured notes unchanged — a full `regenerate()` would burn an LLM call to change one string); markdown re-rendered + `notes.md` re-exported, payload rebuilt + immutably written, notes upsert + enqueue in ONE transaction (NOT `finalizeMeetingProcessing`: a rename is not a run, so `lastProcessingError` bookkeeping stays untouched), worker kicked. The old queued payload stays deliverable from its intact file and is terminally closed by the D12 supersession sweep when the new hash delivers — visible, never silent. Notes-pending `ready` meetings (D17) skip the re-mint — the marker must survive, and the self-heal's own finalize mints with the renamed title. Non-ready meetings take only the title + `updatedAt` write; their next content run mints. The re-mint builds from the meeting row RE-FETCHED inside the chained write (stored-row discipline, matching finalize/enqueue — never the in-memory row). A rename submitted while a processing run is in flight queues BEHIND it on the single-flight chain by design: the commit awaits silently and the title visibly updates when the run drains. A rename or done-toggle failure (DB-error class) surfaces in the window's `AppUIState.lastActionError` banner — never swallowed. Crash window (same class as the documented D17 L-2): a crash between the title write and the enqueue leaves the rename local-only until the next content run — the queued old-title payload still delivers from its intact file.
- **`MeetingDetailView`:** notes rendered NATIVELY from `NotesStructured` (sections as SwiftUI views — the premium layout the renderer's markdown can't deliver through `Text`); the `detailedNotes`/`summary` bodies render through a small block-level markdown view (split on PresentationIntent blocks → paragraphs/lists as stacked SwiftUI views — plain `Text` collapses block intents, pinned here)... parsing via `AttributedString(markdown:, interpretedSyntax: .full)` (**pinned: .full preserves raw HTML as literal text — empirically verified; the N8 html-off assertion holds under exactly this option, asserted in a test**); the user-action-items section visually prominent (the D16 teal box); header: title, date (DD/MM/YYYY), duration, attendees, engine provenance line (quiet, honest); a transcript tab (speaker-labeled, monospace-adjacent, searchable in-view); a regenerate button (engine-respecting, C7 `regenerate()`); processing state overlay while the pipeline runs (stage from the C7 progress stream); `processingNote`/`lastProcessingError` surfaced as a quiet banner when present; **Copy All (V1.1):** a visible button per tab (never menu-buried) — Notes copies the rendered `MeetingNotes.markdown` verbatim, Transcript copies the FULL transcript as readable text (`TranscriptCopyText`: one `[h:mm:ss] Speaker: text` line per segment, names falling back to diarization labels), both via NSPasteboard with a transient "Copied" state.
- **`SearchField` (toolbar):** FTS5 search via C1 `TranscriptRepository.search` → results list (meeting title + snippet with the pinned `\u{FFF9}/\u{FFFA}` delimiters mapped to bold-accent); selecting a hit opens the meeting detail transcript tab scrolled to the segment.
- **`SettingsView` (native Settings scene, three tabs):**
  - *Engines:* ASR + summarization pickers from `EngineRegistry` (displayName, kind badge, availability with reason, cost descriptor for cloud); switching writes `EngineSelection` keys IMMEDIATELY (the selection is the user's choice regardless of preparation state); `prepare()` fired eagerly with **pinned UX: an indeterminate progress row under the picker ("Preparing <name>… first use may download models"), failure → the engine's availability reason inline, selection KEPT, the row offers Retry; **consequence stated per slot: summarization has the runtime fallback; a dead selected ASR engine FAILS processing runs with its named reason until remedied (no silent swap — C2)**, success → row clears; retry also fires on next app launch for a selected-but-unprepared engine**; per-engine config from `configDescriptors` (secrets → masked field → Keychain; the Claude `apiKey` lands here — Q5's touchpoint).
  - *Identity & handoff:* UserIdentity (name/aliases/email), handoff hosts/user/identityFile/remoteRoot (validated per C8 regexes; invalid → inline error, worker pauses as configurationInvalid), extension shared secret (reveal/regenerate per C12), queue panel: HandoffSnapshot display PLUS the contracted controls — **Retry Now** (re-enters `failed` rows incl. ONE re-check of `damaged:` rows; `superseded:` never — the C1/C8 prefix contract; enabled also when items are merely pending on a backoff floor, since the kick clears all floors and benches — the relaunch-to-retry fix), per-item retry, and an automatic `worker.kick()` whenever handoff settings pass validation (C8's fix-resumes-immediately guarantee).
  - *Usage:* cloud spend (CloudSpendLedger month view, ceiling setting `cloud.ceilingUSD`, the 80% warning surfaces here), data root path display.
- **Import:** File → Import Meeting Audio… (WAV/M4A picker) → title + date + optional attendees + optional Meet code sheet → `importMeeting(sourceURL:title:startedAt:attendees:meetingCode:)` — the seam WIDENED from C7's pinned WAV-only form (C7 amendment recorded in its changelog: source may be WAV or M4A — M4A skips the encode [it already IS the retained format, copied in verified]; startedAt and meetingCode persisted); meetingCode also EDITABLE later (detail inspector) — the edit triggers a pending-events sweep, and the dispatch targets the meetings the sweep reports as having RECEIVED ingested data (under a recurring code that may not be the edited meeting; the edited meeting is dispatched only if it received something itself); **any resulting processing dispatch is STATUS-DEPENDENT: `ready` → `regenerate()` (never-regress), non-ready → `process()`** (the rule for every programmatic kick in this chunk) → `process()` kicked; the new meeting appears in the library immediately with live stage progress. (Drag-drop onto the window: same path.)
- **Immediate notes surfacing (DoD):** on `PipelineEvent.stageFinished(.finalize)` the meeting's detail refreshes; the row gets a subtle "ready" pulse PLUS a textual "Ready" badge (not color/motion-only — accessibility); Reduce Motion suppresses the pulse. No notifications ever.
- **Sidebar "My Action Items" (load-bearing, defined):** flattened `structured.userActionItems` across meetings, grouped by meeting, recency-ordered; each row = item text + meeting title/date; selecting opens the meeting detail at the user action-items box (name-driven title: `<name> — Action Items` / the neutral "My action items" when unnamed, G3).
- **Action-item done/archive (V1.1, migration v7):** every user action item — in the detail's user action-items box AND the sidebar's "My Action Items" — carries a click-to-toggle done checkbox; done items move into a collapsed "Completed" group. Persistence: `action_item_state {meeting_id FK CASCADE, item_key TEXT, done_at DATETIME, PK(meeting_id, item_key)}` where `item_key` = SHA-256 hex of the case/diacritic-folded, whitespace-collapsed item text (`ActionItemKey`) — items are LLM output with no stable ids, so an item regenerated VERBATIM keeps its mark and an item whose text changed loses it (documented honestly; fuzzy matching risks marking the wrong item done). Chosen consequence (test-pinned): two DISTINCT items in ONE meeting whose texts fold equal share the key and therefore share done state — they toggle together in both surfaces. Done state is LOCAL ONLY: the payload builder does not read it and the evidence payload gains no fields — `ready` payloads stay re-materializable byte-equal (test-pinned through the durable path: the payload rebuilt from stored state before and after marking done is hash-identical).
- **Main-window record button (V1.1):** a toolbar start/stop control in the library window routed through the SAME `AppEnvironment.toggleRecording` as the menu bar / ⌥⌘R; its label mirrors `captureStatus.state` honestly (recording/warning → Stop; idle/alarm/processing → Record, with the alarm/processing context in the help text — a start is legal from both, only a live session blocks).
- **Accessibility floor:** ⌘F focuses search; state glyphs carry VoiceOver labels; Reduce Transparency swaps glass for solid; standard focus order.
- **Meet-events listener (C12 consumer):** `MeetEventsListener` actor in BlaiseApp: binds 127.0.0.1:18429 (`NWListener`); implements every obligation of docs/meet_events_contract.md:
  - *Crypto + acks:* AEAD decrypt (key = SHA-256(secret)); EVERY response (200/400/401/5xx) carries the signed ack (ackKey = SHA-256(secret||"ack"), status-bound). **Status semantics pinned:** 200 ONLY after durable acceptance (DB write committed); 401 = decrypt failure; 400 = decrypts but structurally unusable (never retried by the extension — so 400 is reserved for true schema garbage, NEVER for transient conditions); replayed and stale-but-valid batches → 200-acked, not ingested (the contract's fork pinned: stale = acked-and-dropped, not 400).
  - *Identity:* isSelf substitution (UserIdentity.name) + the **localized-self denylist {You, Você, you, você} → treated as isSelf** + participantID identity-merge.
  - *Replay/freshness:* per-meeting seen-ids PERSISTED (`meet_seen_event_id` — authoritative POST-match; PRE-match, `meet_events_pending` carries `UNIQUE(batch digest)` so replayed unmatched batches store once) + ±48 h freshness. **Per-batch ingestion is ONE transaction** (seen-ids + speaker events + pending-row removal commit together; the 200 responds after that commit — no crash point can record a batch as seen without its events).
  - *Correlation (machinery complete in C10; live-session case activates at C11):* `Meeting.meetingCode: String?` (NEW column, migration v4, C1-amendment recorded) — set by the import sheet's optional "Meet code" field in V1, by C11 capture sessions later. Triggers: batch arrival → match against meetings (code + window overlap, recurring-code tiebreak by greatest overlap); meeting creation/processing start AND `regenerate()` AND meetingCode edits → sweep `meet_events_pending`; purge >7 d at startup + a daily timer. The C11 seam: `RecordingSessionProviding` protocol (currentSession() → {meetingID, meetingCode}?; C10 ships a nil-returning default — live correlation = match against the active session FIRST and ONLY when `batch.meetingCode == session.meetingCode`, both non-nil (a nil-code session — in-person/zoom — never claims Meet batches; ring-flushed batches from an earlier call can never attach to the wrong live meeting); C11 swaps the implementation).
  - *Roster consumer (the other half of the extension's purpose):* a matched batch's `roster` entries (isSelf skipped — the user is not his own attendee; identity-merged; deduped by folded name; names already present as attendees never queue) land in **`meet_roster_pending`** (migration v5). **Ingestion NEVER mutates the meeting row**: `attendees` and `updated_at_ms` are payload-builder inputs, and a post-mint mutation would make C8's re-materialization recovery (rebuild from durable state must hash-equal the stored version_hash) impossible. The NEXT content run absorbs queued rows into `Meeting.attendees` as `AttendeeSource.meetExtension` inside its entry transaction (where updatedAt legitimately bumps) and clears them — silent attendees thereby reach C4's allowed-name set and that run's NEW payload. An arrival-time ingest that adds content (stored events or roster rows) to a meeting already `ready` fires the status-dependent dispatch (→ `regenerate()`: re-snapshot, re-mint, supersede), fire-and-forget so the 200 never waits on a run; the cost is one full re-run per post-ready flush, and the common case is a single post-meeting flush (deduped replays add no content and never re-fire). *Events consumer table:* matched events land in **`meeting_speaker_event`** (migration v4: meeting_id FK, **dedupe_id TEXT — computed from PRE-substitution WIRE fields per the contract formula and persisted explicitly (identity renames can never break replay protection)**, display_name [post-substitution], participant_id?, is_self, start_epoch_ms, end_epoch_ms; UNIQUE(meeting_id, dedupe_id)) — THE durable home C7's stage 8 reads (`hints from stored events` is now defined: SpeakerHints.activeSpeakerEvents = this table's rows for the meeting).
  - *Migrations v4 + v5 (full shapes, C1 changelog amended):* v4: `meeting.meeting_code TEXT NULL`; `meet_events_pending {id PK, meeting_code TEXT, batch_json TEXT, batch_digest TEXT UNIQUE (SHA-256 hex of the decrypted plaintext — the §replay pre-match dedupe), captured_at_ms INTEGER, received_at DATETIME}` + index on meeting_code; `meet_seen_event_id {meeting_id TEXT, event_id TEXT, PK(meeting_id, event_id)}`; `meeting_speaker_event` as above. v5: `meet_roster_pending {id PK, meeting_id FK CASCADE, display_name TEXT, display_name_folded TEXT, participant_id TEXT NULL, is_self BOOLEAN, UNIQUE(meeting_id, display_name_folded)}`.
  - *Resilience:* port occupied → log + Settings banner + rebind retry every 60 s (banner clears on success).
  - **The C12 golden fixtures are consumed by this chunk's tests** (wire → decrypt → obligations → expected_ingestion.json events present in `meeting_speaker_event`).
- **Observation plumbing:** GRDB ValueObservation drives the library list and detail (meetings, notes); the pipeline progress stream and HandoffSnapshot feed `@MainActor @Observable` holders (C8's pattern).
- **Handoff persistent-failure surfaces (D21, refining hard floor 8 by owner directive; worker-side threshold + `HandoffWarning` value in C8 §persistent-failure warning):** all driven by `HandoffSnapshot.warning` through `HandoffStatusHolder`; transient unreachability shows nothing (the floor stands). While a warning is active: (a) **menu bar** — the MenuBarExtra glyph swaps to an orange `waveform.badge.exclamationmark` in the quiet states (idle/processing/grace; recording/alarm displays keep priority), and the menu names the state (`warning.message()`) with a **Retry Delivery Now** item; (b) **main window** — a dismissible glass-capsule banner over the split view's top: "Evidence Store unreachable since `<time>` — `<n>` meeting(s) waiting. Last error: `<short reason>`" with **Retry Now** and **Open Settings**; dismissal silences THAT episode only (`HandoffStatusHolder.dismissWarning`; a distinct error class or a newly enqueued PERSISTENT failure re-arms the episode with a new `episodeKey`, which un-dismisses the banner and fires a fresh notification — dismissal never silences the feature, and the menu badge is unaffected); (c) **Notification Center** — ONE notification per failure episode via the C14 `AutomationNotificationAdapter` (fixed identifier, so a newer episode replaces the older; denied permission falls through the adapter's quiet post failure, with the banner + badge as the load-bearing surfaces), the holder dedupes on `episodeKey` so attempts never repeat it. **Clicking the notification** (`handoffWarning` category, body-click only — no button) routes through the adapter's `onAction` to increment `AppUIState.openMainWindowRequest` and activate Blaise. The request observer lives on the **always-alive MenuBarExtra label** (`MenuBarLabelWithWindowRouting`), not on the WindowGroup's content: the MenuBarExtra view tree renders for the whole app lifetime, so a click can RE-OPEN a closed main window (the normal state for a menu-bar recorder between reviews) — an observer inside the WindowGroup would have been torn down with the window it must reopen. It calls `openWindow(id: "main")` + `NSApp.activate`, surfacing the banner and the Settings → handoff panel. **Episode bookkeeping is persisted** (`HandoffStatusHolder.EpisodeState` in `app_setting`): a relaunch with the SAME ongoing episode does not re-notify or resurrect a dismissed banner, while a NEW episode after relaunch still notifies. **Launch grace:** the episode NOTIFICATION is suppressed until the worker completes its first post-launch delivery sweep (`markFirstSweepComplete`), so a stale queue that drains right away never fires a notification that would withdraw seconds later — the banner/menu surfaces still show immediately. When the warning clears (the armed undelivered set delivered), every surface clears silently and the standing notification is withdrawn — no success spam. Retry routes through `HandoffWorker.retryNow()` (C8). Demo scene `BLAISE_DEMO_SCENE=handoffwarning` publishes a fake warning snapshot to the holder (UI mirror only) for screenshot/smoke evidence.
