## Goal

The user never babysits start or stop. When any Meet call becomes active in their browser, a Notification Center notification with a **Record** button appears — one click starts a correlated recording. When the meeting ends, the recording stops **by itself**, with a resume grace window (default 5 minutes; Settings-configurable 1–10 minutes or Off) during which rejoining the same meeting resumes it instead of creating a new one. One minute before a calendar event with a Meet link, a **Launch & Record** notification opens the link in Google Chrome (never Safari — the extension lives in Chrome) and starts a recording carrying the event's title and attendees. B-6 manual start/stop keeps working unchanged; no auto-START without a click (B-6 stands — the click moves into the notification). No new network surface: the extension→listener loopback channel (C12 AEAD/ack contract) remains the only one.

## Wire schema v2 — lifecycle signals (extension, `docs/meet_events_contract.md` amendment)

The batch plaintext gains one OPTIONAL field and bumps `schemaVersion` to **2**:

```json
"lifecycle": { "kind": "call-started" | "call-ended" | "heartbeat",
               "atMs": 1781136000000, "reason": "left" | "pagehide" }
```

- **Listener compatibility:** the ingestor accepts `schemaVersion ∈ {1, 2}` (a v1 batch is a v2 batch with no lifecycle; buffered pre-update batches still ingest). Everything else — AEAD parameters, signed acks, status semantics, ring, dedupe ids, correlation — is UNCHANGED.
- **`call-started`:** emitted by the content script on the lifecycle machine's idle→in-call transition (`createLifecycle.onJoin` — the existing joined-state detector; the pre-join lobby already produces nothing). The batch carries the current roster (content as usual) plus the lifecycle field, `atMs` = transition epoch. Tab reloads re-fire it by design; the APP debounces (it has the durable state — see the tracker below). Buffered like any batch: a `call-started` still sitting in the ring when the app comes back covers "app was dead at JOIN time" (the fresh-signal rule below decides whether to notify). It does NOT cover an app crash mid-meeting — by then the `call-started` batch was delivered and removed from the ring long ago, and the extension stays in-call (no new idle→in-call transition occurs), so only heartbeats and content batches follow; the tracker's late-start rule (below) is what recovers that case.
- **`call-ended`:** emitted on in-call→idle. `reason: "left"` = the 1 s poll lost the in-call UI (Leave clicked, host ended, Meet swapped to the disconnected/rejoin screen); `reason: "pagehide"` = the pagehide handler fired (tab/window closed, navigation, browser quit when the handler gets to run). It RIDES the existing final-flush batch (closed events + roster + lifecycle in one batch — atomic ordering, no extra POST). Buffered like any batch.
- **`heartbeat`:** emitted every 60 s while in-call, SKIPPED when any other batch shipped within the last 60 s (roster churn and speech already prove liveness). Heartbeat-only batches are **volatile**: `DeliveryManager.enqueue(…, volatile: true)` attempts one POST and drops on ANY failure — they never enter the ring (a stale heartbeat is worthless and would only displace real events; the 10k-event/200-batch caps stay honest). Chrome's intensive timer throttling exempts audible tabs, and a Meet call is audible; the residual throttling risk is absorbed by the watchdog's 5-minute threshold. Heartbeat-only batches matched to no meeting are NOT stored pending (content-free).
- **Replay/staleness guard (listener):** lifecycle is a CONTROL signal, not content — it is never stored in `meeting_speaker_event` and never rides the per-meeting seen-id set. Instead the tracker keeps ONE per-meetingCode `lastSignalAtMs` covering BOTH signal kinds: a lifecycle signal's `atMs` and a per-batch liveness signal's `capturedAtMs` feed the same monotonic guard, and any signal whose timestamp is ≤ the stored value is dropped — it advances nothing and fires nothing. The watchdog's `lastSignalAt` and every tracker freshness test therefore read EVENT time (`atMs`/`capturedAtMs`), never receipt time: a replayed ciphertext (which the per-meeting dedupe set absorbs as an accepted, zero-new-events batch) or an out-of-order ring flush carries an old timestamp and can neither re-fire a notification nor keep feeding a dead meeting's watchdog. Independently, the existing ±48 h batch freshness gate still applies first.

## App-side tracker (`MeetCallTracker`, BlaiseCore — the C14 brain, clock-injected, fully unit-testable)

A single actor consuming three inputs — signals forwarded by the ingestor (lifecycle fields plus a per-batch liveness signal for every accepted batch that carries a meeting code — correlated or NOT: a declined meeting has no recording to correlate with, and its heartbeats must keep its suppression record alive; fire-and-forget AFTER the ingest transaction, the signed 200 never waits on it), recording-controller events, and a 30 s evaluation timer — and owning four behaviors:

1. **Meet-start notification.** On a FRESH `call-started` (received with `now − atMs ≤ 120 s` — buffered-stale ones only update bookkeeping) for code X: post the notification UNLESS (a) a recording with `meetingCode == X` is active, (b) X is in grace (that is a rejoin → auto-resume instead, below), or (c) X has a live suppression record (the per-call do-not-nag memory, below — the user said no once; do not nag). Notification: title "Meeting in progress", body = the meeting code plus the calendar event title when a current `CalendarSuggestionBuilder` suggestion carries the same code; category `meetStart`; **the default (body-click) action AND the single "Record" action button both start the recording** (benchmark: one click anywhere, no hover-expand hunting; swipe-to-clear = decline). Starting attaches `source: .meet`, `meetingCode: X`, and the matching suggestion's title/attendees when present — the C12 live-correlation seam (`currentSession()`) links roster/speaker events from the first batch. The notification is withdrawn when a recording for X starts by any path or when X's `call-ended` lands. **Late start (app was dead or launched mid-meeting):** the ingestor forwards a per-batch liveness signal (meetingCode, capturedAtMs) for EVERY accepted code-carrying batch — correlated or not, lifecycle-bearing or not (the watchdog's `lastSignalAt` needs this anyway); a FRESH liveness signal of any kind — heartbeat, roster, speech — for a code with no active recording, no grace state, and no live suppression record is treated as `call-started` for notification purposes, so the "Meeting in progress" notification posts late (within ~60 s of relaunch — the heartbeat cadence; heartbeats are volatile and never ring-buffered, so a live one proves the call is current). Stated honestly: the stretch between the app's death and the user's click is not recorded — there is no auto-start without a click (B-6). **Per-call suppression record (the do-not-nag memory).** The tracker keeps at most one suppression record per meetingCode, in one of two states: **`notified`** — created (or kept) whenever the meet-start notification for X posts, by either path (fresh `call-started` or the late-start rule); a posted-and-ignored or swiped-away notification is exactly this state, so a declined meeting is suppressed for the rest of its call, not for a rolling 10 minutes; and **`stopped`** — created when a recording whose code is X is MANUALLY stopped (B-6: the user deliberately stopped, possibly while staying in the call — neither the late-start rule nor a reload's re-fired `call-started` may re-offer Record for that call). Transitions: every fresh signal for X (lifecycle or liveness, post-monotonic-guard) refreshes the record's `lastSignalAt` WITHOUT re-posting — heartbeats arrive every 60 s for the whole call and must never re-nag; a recording for X starting by ANY path clears the record (the active/grace gates (a)/(b) take over; the next manual stop or post re-creates it); and a record EXPIRES only by signal silence — 10 minutes with no fresh signal for X (ten missed heartbeats: the call's signal source is gone, not throttled). `call-ended` does NOT clear it: a tab reload's pagehide emits `call-ended` and the rejoin re-fires `call-started` minutes later, so clearing on `call-ended` would re-nag exactly the reload case; `call-ended` merely stops the signals, and the silence expiry follows ≤ 10 min behind. Accepted trade (stated): a genuinely NEW call on the same code within 10 minutes of the old call's last signal stays suppressed — recurring Meet links reuse codes across days, not minutes, and B-6 manual start always works. **Record clicked while a DIFFERENT recording is active:** if the active recording's code IS X, the click is a no-op and the notification is withdrawn (the gating should have suppressed it; this closes the race). Otherwise — another code, or a code-less manual recording — the click is the same explicit back-to-back signal as the calendar action: the controller stops the active recording first (immediate finalize, no grace) and starts the correlated one (the existing start-while-finalizing support carries it). Never a silently swallowed `alreadyRecording` throw: if the previous stop has not released its session after the 5 s poll budget, or the start itself throws, the dropped click surfaces in the menu's `lastActionError` line.
2. **Auto-stop with end-debounce.** On `call-ended` for the ACTIVE recording's code: enter end-pending and start a **25 s** countdown. (A `call-ended` that lands in the start-instant race — the controller session already exists for the code but the detached `recordingStarted` fact has not been delivered yet — is buffered per code and anchors the debounce the moment the fact arrives; an unconsumed buffer is dropped after the debounce span, so it can never insta-stop a later recording on the code.) Any guard-passing signal for the same code within it cancels — `call-started`, `heartbeat`, or plain liveness, fresh or buffered-stale (Implementation notes, item 1). The debounce absorbs only the FAST flickers (signal-ordering races, Meet's automatic reconnects); a real tab reload lands on the pre-join/rejoin screen — which produces nothing until the user clicks Rejoin and the join completes, routinely longer than 25 s — so a reload usually DOES stop the recording and is recovered by GRACE instead: the post-rejoin `call-started` auto-resumes as part n+1, at the cost of one part boundary and a stitched-silence gap, with no audio of the live call lost. Grace, not the debounce, is the reload safety net. On debounce expiry: `RecordingController.stop()` (the normal verified-encode stop) and the meeting enters **grace** under the §4 entry conditions (Resume window not Off, ≥ 1 recoverable part; otherwise it finalizes immediately, per §4). No user interaction; no notification for a clean, signal-confirmed end (calm by default — the watchdog case below is the exception).
3. **Watchdog (the unobservable ends).** Armed for a recording only once ≥ 1 correlated extension signal has been received for its code during THIS recording (a Meet recording without the extension running must never auto-stop). An evaluation (every 30 s) is **stale** iff `now − lastSignalAt > 5 min`; the FIRST stale evaluation records `staleSince` = current process uptime; the watchdog FIRES on a later stale evaluation whose uptime is ≥ `staleSince + 90 s` with no fresh signal in between (any fresh signal clears `staleSince`). Uptime is the process-monotonic clock that does not advance across sleep — a sleep/wake gap cannot satisfy the 90 s confirmation, and post-wake heartbeats get a full window to resume. Firing → auto-stop, then exactly what §4 pins for any auto-stop: when the Resume window is configured (1–10 min) AND the stop left ≥ 1 recoverable part, the meeting enters grace and the watchdog posts a "Recording stopped — meeting appears to have ended" notification whose default/`Resume` action resumes (the watchdog is the low-confidence path; with grace on, a false stop is one click from recovery and the grace window is the safety net). The Resume notification is withdrawn when its grace window ends by ANY path — resume, expiry, Finalize now, manual stop — a stale "click to resume" hours later would be a dead surface. When the Resume window is **Off**, the stop finalizes immediately like every §4 Off auto-stop and the notification degrades to the informational variant — "Recording ended — uncertain signal", NO Resume action: there is no grace to resume into, and a dead button would be worse than honesty. Off means Off, and the trade is stated plainly: under Off a watchdog false stop of a still-live meeting is a finalized meeting; re-recording the rest of the call is one click on the late-start "Meeting in progress" notification once signals return (or a B-6 manual start) — a NEW meeting, not a resumed part. A watchdog stop that left NO recoverable audio never enters grace regardless of the setting (§4): the existing loud no-audio alarm fires and only the informational variant posts. Covers: browser/renderer crash, browser quit whose pagehide flush never delivered, extension disabled mid-call, network drop that froze the DOM. Residual risk (stated): the whole SIGNAL-CHANNEL-death class — extension removed or disabled mid-call, the listener no longer serving, Chrome relaunched into a profile without the extension — can false-stop a still-live meeting at ~5–6 min, and resume signals can never arrive over a dead channel; the recovery surfaces are the Resume notification AND the grace menu section's **Resume recording** item (the menu is the load-bearing surface when notifications are denied — see the denied mode below). Under Off neither surface exists and none is faked: the informational notification — or, with notifications denied, the stop simply appearing as the most recent meeting in the menu — is all Off gets; that is the setting's accepted meaning, not a hole.
4. **Resume grace window.** After an auto-stop (debounced end or watchdog) whose finalize left **≥ 1 recoverable part**: the meeting holds in grace for the **Resume window** setting (default **300 s**; Settings stepper 1–10 min plus **Off** — see the Settings section; manual stops are unaffected). An auto-stop that left NO recoverable audio never enters grace — there is nothing to resume INTO; it takes today's no-recoverable-audio stop path exactly (loud alarm, status `failed` with "capture produced no recoverable audio", tracker state cleared, a later `call-started` is a new meeting — see the pinned divergence in the resume mechanics below). **Off** means no grace state is ever entered: an auto-stop finalizes immediately exactly like a manual stop (processing kicks at the stop, the tracker clears its state for the code, a later `call-started` is a new meeting) — including a WATCHDOG stop, whose notification then degrades to the informational no-Resume variant (§3). A fresh `call-started` OR `heartbeat` for the same code → `RecordingController.resume(meetingID:)` (below) — silent, automatic. The `meetStart` notification action and the menu's Resume item resume the same way. Grace expiry → finalize: kick `processCaptured` via the existing track-inventory-aware dispatch. A MANUAL stop never enters grace (B-6 unchanged: stop means stop; the tracker clears its call/grace state for that code AND writes the `stopped` suppression record (§1), so the still-continuing call never re-offers Record; a later `call-started` after that record's silence expiry is a new meeting). A resume signal while a DIFFERENT recording is active is ignored and logged (one session at a time; the grace meeting finalizes at expiry). Grace windows are PER MEETING and stand CONCURRENTLY: a back-to-back auto-stop landing inside a standing window installs its own entry and leaves the standing one untouched — each meeting finalizes at its own expiry, soonest first. At most one window per meeting CODE (the code is the resume key): a same-code auto-stop finalizes the standing window before installing the new one. Signal-driven rejoins and the notification Resume action target their own meeting; the menu's Resume/Finalize items act on the soonest-expiring window — the one the menu displays. Quit during grace: no special path — the meeting's durable state (status `recording`, all surviving parts encoded, no CAFs) is exactly what the existing launch machinery recovers (DB sweep → failed/"interrupted" → `redispatchInterrupted` auto-kicks; notes arrive at next launch, same as quit-during-recording today). This holds even when the FINAL part finalized empty: the empty-part rule in the resume mechanics below keeps the status `recording` whenever earlier parts survive, and `redispatchInterrupted` keys on part-1 `audio*.m4a` — which every meeting in grace has, because grace entry itself requires the just-stopped finalize to have left recoverable audio, so a meeting whose part 1 was empty never entered grace and never grew a part 2 (it went `failed` at the part-1 stop, per the entry condition above).

Status semantics during grace: the row STAYS `recording` (no new status value, no migration churn on the CHECK set) — honest reading: "capture lifecycle not finalized". This claim holds unconditionally because grace is only ever entered with ≥ 1 recoverable part: the no-audio `failed` write and grace can never coexist on one meeting. `endedAt` semantics across parts: every part STOP sets `endedAt` (latest part end wins), and `resume(meetingID:)` CLEARS it at part start — while a part records, the correlation window falls back to its open `endedAt`-or-now form (`matchMeeting` already reads `endedAt ?? now` with ±10 min padding), so events during part n ≥ 2 and a post-crash extension flush after a mid-part crash (which leaves `endedAt` NULL) both still correlate. The stitcher repairs `endedAt` whenever it is NULL at stitch time: open part rows with decodable audio are first closed at `started + decoded part duration`, then the meeting close is the LATEST CLOSED row — a trailing open row with NO recovered audio (kill -9 between the row insert and CAF creation on a resume) never recorded anything and contributes no span; for a meeting with no part rows at all (pre-v8) the close derives from `startedAt + decoded audio duration` — so the library end time is truthful after crash recovery. During grace itself `endedAt` is the latest part end and the Resume-window ceiling (10 min) never exceeds the ±10 min correlation padding around it. Crash during grace = crash during recording as far as every existing sweep is concerned, and they already do the right thing.

## Multi-part capture (the resume mechanics — decision: per-part retained audio + WAV-level stitching at processing)

Three candidates were weighed against the C1 retention rules and hard floors 1–2. **(a) Delayed-finalize** (hold the CAFs unencoded through grace, append/concatenate at CAF level) keeps one pair but leaves the grace window's data one verification short of retained-class and complicates the orphan sweep's live-vs-crashed reasoning for zero benefit — the CAFs are crash-safe either way, but TODAY's per-stop verified encode is strictly stronger. **(b) Multi-part with per-part pipeline runs** (ASR/diarization per part, concatenate transcripts) fragments speaker clusters across parts (S1-in-part-1 ≠ S1-in-part-2; unnamed speakers can never re-unify) and touches C4 voting, interleave, and ord-sequencing — the widest blast radius. **(c) WAV-level stitching at processing** — CHOSEN: each part stop-encodes immediately exactly like today (hard floor 2 per part, unchanged code path), and the transcode stage stitches decoded parts into the ONE temp WAV per track that every downstream stage already expects. Diarization sees one continuous track (cross-part speaker continuity preserved), interleave/voting/payload/regeneration untouched.

- **Artifacts.** Part 1 keeps today's names (`capture_system.caf`/`capture_mic.caf` → `audio.m4a`/`audio_mic.m4a` — zero churn for the overwhelmingly common single-part case). Part n ≥ 2: `capture_system_2.caf`/`capture_mic_2.caf` → `audio_2.m4a`/`audio_mic_2.m4a`. `MeetingPaths` gains part-suffixed variants; the retention contract already covers "every `audio*.m4a`" by construction (the C1 amendment records that `capture_*_<n>.caf` are retention-class identically to part 1, with exactly TWO deletion paths, both named in the amendment: the same single audited verified-encode function, per part; and the zero-frame-stub rule — removal only after a duration probe proves the CAF carries zero audio frames, which today covers start failures and now also covers an empty part-n stop, the identical proof obligation in both places).
- **Durable part metadata (migration v8 — v7 is taken by the in-flight `action_item_state` change, and GRDB identifiers are append-only):** `meeting_capture_part(meeting_id, part_index, started_at_ms, ended_at_ms NULL)`. The controller inserts the row at each part start and closes it at stop. Rows are the stitcher's gap source; a row left open by a crash is closed at stitch time as `started + CAF/m4a duration`; an open row with NO recovered audio for its part is skipped at stitch time (re-anchoring is absolute, so later parts are unaffected). Meetings with no rows (every pre-v8 meeting) are single-part — derived, not migrated.
- **`RecordingController.resume(meetingID:)`:** precondition = that meeting in grace (tracker-owned; the controller just trusts its caller and `active == nil`). Disk precheck, `endedAt` cleared, part row inserted, THEN the new capture session into the next part's CAF paths (row before session — a crash can leave a row without files, which the stitcher already tolerates, but never part files without a row), `.started` re-emitted (indicator back to recording), live session re-registered (live correlation resumes). Stop of part n runs the SAME stop path with part-n paths: endedAt update, off-actor finalize of that part's CAFs, `awaitQuiescence` accounting, alarms — with ONE pinned divergence: **the no-recoverable-audio failed-status write fires only when NO part of the meeting has recoverable audio** — and when it fires, the stop takes today's no-audio path exactly (loud alarm, status `failed`, NO grace; §4 entry condition). At a part-1 stop "no part has recoverable audio" is just "part 1 is empty", so an empty-part-1 meeting fails honestly at its first stop and never becomes multi-part — there is no part-2-into-a-`failed`-row case and no quit-during-grace state for the sweep to miss. An empty part n ≥ 2 with surviving earlier parts raises the existing loud alarm but leaves status `recording`; grace continues, and the surviving parts finalize and process at grace end — or, after a quit during grace, through the unchanged sweep → `redispatchInterrupted` path. Never a silent loss. The empty part's ROW follows its files: the row is deleted ONLY when every file of the part is provably gone — its zero-frame CAFs removed per the C1 zero-frame rule (duration probe proves zero audio frames) and no part m4a on disk — so deletion can never strand a part file without a row. An encode-FAILED part whose CAF is retained (hard floor 2) KEEPS its open row: the state stays honest, the next launch's part-aware CAF sweep can still rescue the encode, and a rescued `audio_n.m4a` then stitches at its row's exact re-anchored offset instead of surfacing as a row-less suffix append; until rescued, an open row with no recovered audio is skipped at stitch time (above), so the stitcher never sees a phantom span either way. The processing kick moves from stop to grace expiry for auto-stops; manual stops kick immediately as today.
- **Stitching (transcode stage, captured meetings only):** enumerate parts (DB rows ∪ part files on disk); ONE part → exactly today's AUDIO path, byte-for-byte identical output on the decode/transcode side; the one deliberate behavior change vs today is the metadata repair — the NULL-`endedAt` repair below applies to single-part meetings too (a post-v8 crash recovery leaves one open row and a NULL `endedAt`, and the library end time must be truthful there as well). Multiple parts → decode each part m4a to WAV and emit per track with **per-part wall-clock re-anchoring**: part n's target offset is `offset_n = part[n].started − part[1].started`, and the silence inserted before part n is `offset_n − samples already emitted`, clamped ≥ 0. Re-anchoring (rather than summing `started − ended` gaps) means per-part decoded-duration error — the encode-verification tolerance alone allows 0.5 s per part — never accumulates: every part boundary lands at its exact time-since-meeting-start, so the C12 speaker-event epoch correlation, the two-track interleave, and the drift-sweep duration reference all hold with zero changes. A part FILE with no `meeting_capture_part` row (possible only as residue — the insert order above closes the normal window, and the empty-part rule deletes a row only when no file of the part remains) has no span: it is appended in suffix order with zero inserted silence and a capture-recovery note recorded — honesty over an invented gap. A part missing one track (e.g. mic part 2 damaged, CAF retained) contributes silence for that span on that track plus the existing capture-recovery note (third writer class — survives run-entry clears).
- **Silence-hallucination guard (hard floor 1):** the run context records the gap ranges; after ASR, segments lying ENTIRELY inside a gap range (shrunk by a 1 s margin on each edge) are dropped per track before normalization, with the drop count logged in the run record — Whisper-class models hallucinate on long silence, and a stitched gap is the one place silence is structural, known, and provably speech-free.
- **Orphan sweeps:** the CAF startup sweep and `finalizeTracks` become part-aware (glob `capture_*_<n>.caf` alongside the unsuffixed pair); the live-session skip rule and the launch re-dispatch are unchanged (status `recording` + DB sweep semantics already cover grace, above).

## Calendar pre-meeting notification (`PreMeetingScheduler`, BlaiseCore + EventKit adapter)

`CalendarSuggestionBuilder` stays the parsing/matching core; the scheduler extends it into time:

- **Input:** `CalendarEventSnapshot` gains `eventIdentifier: String` (the EKEvent identifier, mapped at the adapter). The adapter re-fetches a rolling 24 h window every 5 min and on `EKEventStoreChanged`. Armed ONLY when EventKit access is already granted (the existing graceful opt-in; no new prompt path — denied/absent calendar = no scheduler, manual unaffected).
- **Firing rule:** events with a parsed Meet code fire ONE notification at `start − 60 s` (fired-set keyed by `eventIdentifier + start`, in-memory; after an app restart an event still inside [start − 60 s, start + 15 min] whose code is not recording, not in grace, AND not already done — done meaning a meeting row with that code whose `endedAt` falls inside the event window: the call was recorded and ended before the restart, and re-firing Launch & Record would invite recording a dead meeting — re-fires; the fired-set died with the process, so a duplicate notification after a restart is accepted by design: restart must not eat the reminder). Events whose code is already recording or in grace are skipped. Zoom/Teams events are out of scope for V1.1 (open question 3).
- **Notification:** title = event title, body "Starts at HH:mm — opens in Google Chrome", category `calendarUpcoming`; the default action and the single **Launch & Record** button both: (1) resolve Chrome via `NSWorkspace.shared.urlForApplication(withBundleIdentifier: "com.google.Chrome")` and open the Meet URL with `open(_:withApplicationAt:configuration:)` — explicitly NEVER the default browser (Safari may be the user's default and has no extension); Chrome missing/launch failure → a "Couldn't open Google Chrome" notification and NO recording start (recording an unjoined meeting is empty audio, worse than nothing) — then (2) start the recording with the event's title, attendees (user excluded, as today), `source: .meet`, and the meeting code, so the extension's first batch correlates live. If a recording is already active when the action is clicked and its code IS the event's code, the click is a no-op and the notification is withdrawn — the same guard as the meet-start path (both notifications can legitimately coexist for one meeting: calendar fires at T−60 s, meet-start fires on join; the second click inside the withdrawal race must not split the meeting). Otherwise the controller stops the active recording first (normal immediate finalize, no grace — an explicit user action to start the NEXT meeting IS the back-to-back signal; the existing start-while-finalizing support carries it) and then starts the new one.
- **Expiry/withdrawal:** the notification is withdrawn when a recording for its code starts by any path, when `call-ended` lands for the code, and unconditionally at `start + 15 min` — a stale "Launch & Record" sitting in Notification Center hours later would restart the forget-to-stop incident this chunk exists to kill. A click WITHIN validity starts normally: the join follows and the watchdog arms on the first correlated batch (arming requires ≥ 1 signal, per the tracker). If the join never completes — click-and-abandon, a join that stalls in the lobby, or Chrome opening in the wrong profile (`open(_:withApplicationAt:configuration:)` targets the LAST-ACTIVE profile, which may not have the extension) — no signal ever arrives and the watchdog never arms. Backstop: for any notification-initiated recording that has received ZERO correlated signals 15 min after start, the tracker posts ONE "Recording running — no Meet signals yet" notification (menu section under denied notifications). Never an auto-stop (a live meeting recorded without a working extension must never be cut), but never a silent unbounded recording either. Residual risks (stated): never-joined and wrong-profile recordings run until the user acts on that nudge; manual B-6 recordings are untouched by it.

## Notifications plumbing + TCC touchpoint

## Implementation notes (deviations from the original design — current behavior, durable ledger)

The shipped implementation deviates from the v3.1 design in seven places. Each is the CURRENT behavior; the body above already states it where it is load-bearing. None weakens a hard floor.

1. **End-debounce cancel is wider than originally pinned.** Any guard-passing signal for the active code cancels the pending end — plain liveness included, buffered-stale included — not only fresh `call-started`/`heartbeat`. Safe by construction: under FIFO ring delivery plus the per-code monotonic guard, no batch generated before the final flush can carry a newer timestamp, and post-leave the extension emits nothing until a rejoin (whose `call-started` is a legitimate cancel). Replay immunity is pinned by the discriminating guard tests.
2. **The suppression record refreshes on every guard-passing signal,** fresh or buffered-stale — the same widening with the same reasoning: only genuinely newer-timestamped signals pass the guard at all.
3. **Three notification categories are registered** (`meetStart`, `calendarUpcoming`, `graceResume`), not two: UNUserNotificationCenter fixes action titles per category, and the watchdog's Resume action cannot ride the other two.
4. **Volatile heartbeats carry the current loss counters but never reset them.** Counters reset only when a ring-delivered batch's signed 200 confirms the wire that actually carried them; a volatile POST resets nothing (pinned in `extension/test/automation.test.js`).
5. **Zero-frame CAFs at any stop report the track `.absent` — no empty m4a is ever minted.** The provably-empty CAF is removed under the C1 duration-probe rule; an all-empty stop takes the honest `failed` path instead of encoding silence (recorded as the C1 v6.10 / C11 v4.3 amendments).
6. **An encode-failed retained-CAF part keeps its row, and the row is CLOSED at stop** (`ended_at_ms` set by the normal stop path), not left open. The stitcher skips a part on "no recovered audio", not on row openness, so the skip-until-rescued semantics are identical and a rescued m4a still stitches at its row's exact offset.
7. **A write-failure automatic stop is NOT a manual stop for suppression purposes:** the call may still be live and a re-record offer is correct, so no `stopped` suppression record is written (recorded in C11 v4.3).

## Out of scope

Auto-start without a click (B-6 stands; the one-click notification IS the V1.1 answer), Zoom/Teams lifecycle signals (no extension surface exists there), `.timeSensitive`/Focus-breaking notifications (entitlement), a calendar lead-time setting (60 s stays a constant; the Resume window IS a setting, per resolved decision 1), multi-part awareness in the meeting-detail audio player (P1 item; parts list verbatim until then).

## Resolved product decisions (the user, 2026-06-10)

1. **Grace window: 5 minutes default, user-configurable.** Settings gains a "Resume window" control (slider/stepper, 1–10 min, plus "Off" = finalize immediately on auto-stop). The setting only affects AUTO-stops; manual stop never enters grace (unchanged).
2. **Clean auto-stops are SILENT.** A signal-confirmed meeting end stops and finalizes without any notification — true to the silent-and-automatic vision. Only watchdog-triggered stops (uncertain end causes) raise the notification with the Resume button.
3. **Launch & Record is Meet-only in C14.** Zoom/Teams calendar events keep today's fully manual flow; extending launch-only support to them is a recorded BACKLOG candidate (no auto-stop exists there — the forget-to-stop risk would return).
